# Правила разработки HotelFlow

Правила относятся к Go-коду HotelFlow. Соглашения от 11 октября 2026 года включают архитектуру, ошибки, unit-тесты, Go-стиль, DI и логи. Следующие требования пользователя дополняют их. Они не требуют перестройки существующего каркаса вне текущей задачи.

## Перед изменением кода

1. Прочитай [контекст разработки](docs/agent-context.md), [действующую спецификацию](docs/specification.md) и [принятые решения](.agents/references/decisions.md).
2. Для сущностей, use case, обработчиков, DTO, внутренних сервисов и вспомогательных пакетов используй [hotelflow-domain-usecase](.agents/skills/hotelflow-domain-usecase/SKILL.md).
3. Для storage, DAO, SQL, xo, миграций, транзакций и версии сущности дополнительно используй [hotelflow-storage](.agents/skills/hotelflow-storage/SKILL.md).
4. Для API, gateway, событий, Kafka и outbox дополнительно используй [hotelflow-contracts-events](.agents/skills/hotelflow-contracts-events/SKILL.md). Для API Gateway обязательно прочитай [оформление шлюза](.agents/skills/hotelflow-contracts-events/references/api-gateway.md).
5. При изменении Go-кода, ошибок, тестов, логов и проверках результата используй [hotelflow-errors-tests](.agents/skills/hotelflow-errors-tests/SKILL.md). Подробности читай по теме изменения.

Читай только относящиеся к задаче разделы ссылочных документов. Образцы и ограничения их переноса перечислены в [аудите исходников](.agents/references/source-audit.md). Их названия каталогов не отменяют правила этого проекта.

## Актуальная предметная область

Hotels владеет отдельными сущностями Hotel и Room, описанием отелей/номеров, официальными звёздами, координатами, удобствами и min/max длительности. Review владеет только пользовательскими рейтингами отелей; у номеров рейтинга нет. ListHotels/GetHotel обогащаются одним batch RPC в Review, который читает весь набор одним SQL. GetRoom/ListRooms не зависят от Review. Booking владеет гостем, номером, периодом и статусом брони, получает условия из Hotels до транзакции и проверяет занятость в своей БД. Отдельных сервисов Room, Search и Availability нет.

Period — VO [starts_at, ends_at), произвольное начало, UTC, точность до микросекунд. Одна бронь содержит один непрерывный период. Seed Hotels задаёт минимум 12 часов; максимум зависит от номера. Создание одной локальной транзакцией сохраняет CONFIRMED, ключ идемпотентности и outbox. Порядок в транзакции: проверка длительности, insert брони, outbox, commit. Ключ проверяется до вызова Hotels: сохранённый повтор возвращает бронь. При гонке вставок один запрос получает конфликт; advisory lock и повторное чтение ключа в confirm не нужны. Пересечения запрещает EXCLUDE USING gist по room_id и tstzrange; room lock и предварительное чтение пересечений не нужны. Подробности — `docs/booking.md`.

Продакшн-данных нет: текущую модель, исходные миграции и контракты меняем inplace. Не вводи legacy-схемы, перенос старых данных или параллельные версии API/событий ради совместимости. Генерация кода сама не сбрасывает БД.

## Обязательные правила

- API Gateway — исключительно транспортный шлюз по образцу `fault-tolerant-stand/services/api-gateway`: тонкие `internal/app/<область>/v1` напрямую вызывают generated gRPC-клиенты. В шлюзе нет application/usecase, application/service, domain, бизнес-DTO и дополнительного infrastructure/gateway. Клиенты собираются в `initControllers` из map соединений по константам config. Бизнес-правила и сценарии находятся у владельцев данных.
- Clean Architecture и DDD. Доменная логика и инварианты находятся в сущностях/агрегатах и их доменных коллекциях. Use case оркестрирует один сценарий, транспортные обработчики тонкие.
- Пути внутри каждого сервиса: `internal/domain/entity`, `internal/domain/vo`, `internal/application/usecase`, `internal/application/service`, `internal/dto/<область>`, `internal/infrastructure/storage`, `internal/infrastructure/gateway`, `internal/events`, `internal/pkg`.
- Domain не зависит от application, infrastructure, transport, protobuf, xo или БД. Use case зависит от узких интерфейсов, а не конкретных storage/gateway. Ручной DI организуется в `internal/init.go` и `registry.go` слоёв. Registry может импортировать concrete реализации исключительно для сборки зависимостей; это не разрешение на такие импорты внутри бизнес-логики.
- Proto-контракты только локальные: `services/<сервис>/api/<сервис>/<область>/v1`. Общего корневого proto нет. Вся генерация через Buf и `buf.gen.local.yaml`/`buf.gen.external.yaml`; внешние клиенты генерируются из `api` владельца в `internal/pkg/pb/external`. Прямые вызовы protoc запрещены для генерации проекта.
- Имена внешних gRPC-сервисов объявляй константами в `config` (`BookingService`, `HotelsService`, `ReviewService`). Исходящий infrastructure/gateway registry сервиса-владельца принимает `map[string]grpc.ClientConnInterface`, выбирает соединения по этим константам и создаёт клиентов. В `initGateway` передаётся вся map; открытие и закрытие соединений остаётся в lifecycle.
- Исходящий gateway сервиса-владельца следует форме `ExternalClient` → `NewExternalClient(conn)` → `Client{external}` → `NewClient(external)`. Входящий context передаётся напрямую, без собственных timeout. Данные уже имеющейся сущности передавай в gateway самой сущностью, если промежуточный DTO только копирует её поля.
- Время в use case получай напрямую через `time.Now()`; сущностям передавай готовое `time.Time`. Не добавляй `now func() time.Time`, Clock-интерфейсы, поля часов и параметры часов в конструкторы/registry. Не заменяй их глобальной изменяемой функцией ради тестов. Доменные границы времени тестируй через явный `time.Time`; сценарии проверяй без зависимости от точного момента запуска.
- UUID создавай непосредственно через `uuid.NewV4()` в сценарии создания брони. Не передавай `newID func()` через constructor/registry только ради тестов. Тест проверяет полученный ID, а не навязывает его значение.
- DAO выполняет простое преобразование xo → `With/Option`. Не добавляй `validateColumns` и повторную валидацию каждого SQL-поля: доменные инварианты проверяет сущность.
- Сущность меняет собственное состояние и версию только доменными методами. DAO обязательно восстанавливает её через `With(id, opts ...Option)` и `With<Field>` из `option.go`. Восстановление не является бизнес-переходом и не создаёт событий.
- Для сохранения нескольких однотипных сущностей используй `Save(ctx, objects ...*entity.Type)` с одним batch SQL, без отдельного имени `SaveMany` и цикла одиночных SQL. CAS проверяет каждую запись; несовпадение числа обновлённых строк возвращает ошибку для отката общей транзакции.
- Каждый storage содержит DAO, встраивающую соответствующую xo-модель. SQL, pgx, DAO и xo не выходят в use case, внутренние сервисы или domain.
- Входной DTO конкретного use case объявляй рядом с ним в `types.go`. Общие DTO остаются в `internal/dto/<область>` только если действительно используются несколькими слоями. В DTO и сущностях нет `json`-тегов: JSON-модели принадлежат транспортным адаптерам или определениям событий.
- Доменные статусы и другие перечисления — в `types.go`, реализация версии — в `version.go`. Валидация состоит из читаемых проверок конкретных инвариантов; не пиши длинные цепочки несвязанных условий и каталоги сырых строк внутри `Booking.Validate`.
- DTO могут иметь методы. Для повторяющейся работы с моделями/DTO/коллекциями определяй осмысленные типы через `type` и методы на них вместо множества однотипных helper-функций. Это не переносит инварианты и переходы сущности из domain.
- Проверку роли и общего контекста запроса выполняет interceptor по полному RPC method; HTTP-вход использует middleware по маршруту. В сервисах-владельцах роли — тип `Role` и константы в `internal/domain/entity/types.go`; DTO использует этот тип. Транспортный API Gateway использует enum внешнего контракта и не создаёт свой domain. Use case не повторяет списки разрешённых ролей; проверка владения конкретной бронью остаётся бизнес-правилом.
- Для одиночного SQL-запроса отдельная бизнес-транзакция и обёрточный метод use case не нужны. Транзакция нужна для группы изменений, которые должны сохраниться атомарно, например состояние брони и outbox.
- Бизнес-транзакция оформляется прямым вызовом `internal/pkg/transaction.Exec`, без поля `exec` или дополнительной DI-абстракции исполнителя. В ней допустима только собственная БД; gateway, Kafka и прочие внешние вызовы выполняются за её пределами. **Исключение по указанию пользователя: отдельный outbox relay может держать свою транзакцию БД во время отправки в Kafka.**
- **Outbox и входящая идемпотентность включены пользователем.** UUID `idempotency_key` задаёт клиент; уникальность `(guest_id, idempotency_key)` обеспечивается БД по образцу module-2/transient-failures. Одинаковый ключ и состав возвращают сохранённую бронь без нового события; другой состав даёт Conflict. `request_id` служит трассировке, не идемпотентности. Не сохраняй PENDING/UNCERTAIN у брони. Автоматические RPC retry отложены. Inbox включён для Booking/Check-in; CAS используется при смене статуса, создание имеет версию 1.
- SQL в storage оформляй многострочными raw string: нижний регистр, табы для вложенности, отдельные строки для select/from/where/join/order by/limit, условий and/or, колонок insert/update и аргументов batch unnest. Длинный запрос объявляй локальной константой рядом с методом, а не внутри вызова Exec/Query. Не выравнивай SQL случайной смесью пробелов и табов. При форматировании сохраняй операции, порядок параметров, условия, сортировку и ограничения. Правило относится и к storage inbox/outbox.
- SQL/DDL lower case. Разрешены primary key, unique и индексы. Для public.bookings разрешены EXCLUDE USING gist по room_id и tstzrange(starts_at, ends_at, '[)'), NOT NULL для room_id/starts_at/ends_at и CHECK конечного непустого периода. Это узкое исключение обеспечивает атомарный запрет пересечений. FK/references, каскады, триггеры и прочие ограничения вне разрешённого списка не добавляй. Условия длительности остаются в домене и Hotels.
- Не добавляй в storage универсальные `storageError`-классификаторы SQLSTATE/сети. Ожидаемые NotFound, CAS-конфликты, 23P01 именно bookings_room_period_excl и 40P01 при вставке брони обрабатываются на месте, остальные технические ошибки передаются с сохранением причины; безопасный русский ответ формирует существующий ErrorInterceptor.
- Исключение для API Gateway: Clay и стандартный gRPC Status JSON без gatewayerror/Problem, прямой proxy ошибок владельца; auth в pkg/auth проверяет только роли, identity проверяет Booking. Не сохраняй third_party — используй Buf dependencies/plugins и внешний кеш при недоступности registry.
- Пакеты ошибок сервисов-владельцев — точная копия `ordererror/error.go` и `option.go`, кроме имени package; разрешено добавлять только значения Code. Не добавляй Reason/resource ID/defaults/свои конструкторы. Все пользовательские пояснения — на русском. ErrorInterceptor владельца отображает Code в status/metadata; API Gateway проксирует их через Clay без собственного пакета ошибок. Подробности и особенности cause — в правилах ошибок.
- Сбор событий строго по образцу: `New(entity) pipe.Func[event.Events]`, `events.Base[Payload]`, сериализация отдельного event payload, headers и `append(batch, event.Event{...})`; use case или прикладной сервис принимает `flusher event.Flusher` напрямую через конструктор и использует `event.Buffer` и `Flush(txCtx)`. Самодельный `[]outbox.Message`/`Enqueue` вместо этого запрещён.
- Outbox, event/pipe, worker и connectors копируй из `fault-tolerant-stand/services/order-service`, адаптируя импорты и конфигурацию. Не заменяй их собственной упрощённой реализацией. Метрики по-прежнему не подключай.
- Инициализация каждого компонента/слоя — отдельный метод в `internal/init.go`: Postgres, storage, gateway, message bus, outbox, services, use cases, controllers. `business.go`/`initBusiness` запрещены. Все контроллеры регистрируются с обязательными зависимостями без nil-fallback; отсутствие зависимости не маскируется режимом Echo-only.
- Основной вид новых автоматических тестов — unit; для однотипных вариантов используй читаемые табличные тесты. PostgreSQL/Kafka/Docker, integration/E2E-фреймворки и порог покрытия не требуются для каждой задачи.
- Оформление всего написанного вручную Go-кода шести сервисов и `hotelctl`: непустые тела функций всегда многострочные, включая getters, Option и анонимные функции. Не объединяй самостоятельные операторы через `;`. Составные литералы с несколькими полями и длинные вызовы конструкторов разбивай по строкам; логические шаги разделяй пустыми строками. Отступы — стандартные табы Go. Сначала раскрой сжатый код, затем примени gofmt/goimports: сами инструменты не раскрывают все однострочные тела. Generated-файлы вручную не форматируй.
- Логи — структурированные через `log/slog`, только значимые события и ошибки, без повторов по слоям и спама. Новые метрики, exporters и dashboards пока не добавлять.
- Не менять generated-файлы вручную. Сначала меняется источник контракта, миграция или шаблон, затем выполняется соответствующая генерация.

## Повторяющийся код между сервисами

Если замечание касается общего подхода (ошибки, DTO, версии, валидация, DI, события, форматирование), проверь все шесть сервисов и исправь применимые повторения. В результате явно перечисли охват и неприменимые участки. Не ограничивайся первым файлом из примера. Каркасу без бизнес-сценариев не добавляй сущности, storage, outbox или зависимости ради единообразия; общие правила транспорта и логирования действуют и в каркасах.

## Завершение изменения

Проверяй изменённое поведение unit-тестами: доменные переходы, оркестрацию, mapping и ошибки. Форматируй изменённый Go-код через gofmt; используй go vet и команды затронутого Go-модуля из Makefile. Текущий `make -C services/<service> test` запускает `go test -race ./...` и включает также существующие lifecycle-тесты с процессом/портами: не называй весь target unit-only. После изменения контрактов выполняй целевую генерацию. Не запускай reset БД как часть обычной генерации.

В результате укажи изменённое поведение, выполненные проверки и оставшиеся ограничения. Не добавляй скрытые защиты для исправления намеренного учебного дефекта.

## Check-in ↔ Booking: request/reply

Booking владеет бронью, её статусом и занятостью номера. Check-in владеет сущностью `CheckIn`: ожидаемым прибытием и его оформлением. Связь — `booking_id`; сущности Booking/Operation, копии статусов/версий Booking и сервисы `booking/request` в Check-in не нужны. Данные о госте, номере и периоде поступают из события создания для оформления заселения. Сервисы не читают чужую БД. Подробности — [docs/check-in.md](docs/check-in.md).

- Каждый RPC реализуется в отдельном файле `internal/app/<область>/v1/<метод>.go`. `service.go` содержит структуру и конструктор с конкретным `*usecase.Registry`. Не объявляй интерфейсы use case на уровне gRPC-хендлеров. В API Gateway остаются generated downstream-клиенты.
- UUID и response mapping находятся в самом методе, как в ad-service: `uuid.FromStringOrNil`, `lo.Map` либо простой цикл. Отдельные `parseID`, `bookingView`, `operationView`, `response.go` и универсальные мапперы не нужны. Обязательные ID проверяет use case/сущность; общую identity и роли — interceptor.
- Один use case на RPC **и один use case на сценарий входящего события**. Kafka-хендлеры вызывают именно use case. Вход — локальный `types.go`; optional поля — `mo.Option[T]`. Не создавай дополнительные use case для отдельных шагов одного сценария.
- `booking.confirmed.v1` регистрирует ожидаемое заселение. Check-in отправляет `checkin.arrival-requested.v1` или `checkin.cancellation-requested.v1`. Booking отвечает `booking.activated.v1` / `booking.canceled.v1` (пакеты `booking_activated` / `booking_canceled`); для бизнес-отказа — `booking.checkin-rejected.v1`. Обобщённого changed нет.
- **Ключ идемпотентности события — `correlation-id`**: один UUID создаётся при формировании события до записи outbox, сохраняется в `x-correlation-id` и `correlation_id` envelope. Relay при повторе не создаёт новый ID. Ответ — самостоятельное событие со своим ID; `causation_id` указывает ID запроса. HTTP `request_id` служит трассировке. Ни event_id, ни Kafka offset, ни request_id не подменяют ключ события.
- Подписчик проверяет заголовок и envelope, сохраняет inbox с этим correlation-id и только затем подтверждает offset. В inbox уникален `(correlation_id, topic)`. Реализация пакета inbox — копия payment-service с адаптацией импортов/форматирования; уникальность ключа усиливает DDL, не меняя алгоритм копии.
- Booking сохраняет CAS-переход и reply outbox одной транзакцией. Inbox может повторно вызвать use case после business commit: идемпотентность обеспечивает доменная логика, без AcceptEvent и отдельной таблицы обработанных событий. Повторная активация ACTIVE и отмена CANCELED не меняют состояние/версию; поздняя активация CANCELED не восстанавливает бронь. Reply допускается повторно: у него новый correlation_id и прежний causation_id, Check-in проверяет версию действия. Техническая ошибка возвращается inbox для retry.
- Check-in сохраняет HTTP-ключ `(actor_id, key)`, своё состояние и outbox одной транзакцией. `insert ... on conflict` и CAS обеспечивают конкуренцию без явных advisory/row locks в этом сценарии. Таблица requests — технические ключи, без отдельной сущности/жизненного цикла Operation. Повтор того же ключа и booking_id/action возвращает текущее состояние того же CheckIn, другой состав — Conflict.
- CheckIn: EXPECTED → ARRIVING → CHECKED_IN; отмена EXPECTED/CHECKED_IN → CANCELING → CANCELED. Ошибка Booking возвращает предыдущее состояние и русское пояснение. Ответ применяется только к ожидаемой версии собственного CheckIn; поздний ответ не меняет новое состояние. Это корреляция ответа и защита от устаревшего действия, не второй ключ дедупликации события.
- Booking: CONFIRMED → ACTIVE, отмена CONFIRMED/ACTIVE → CANCELED. Активация проверяет время исходного действия в пределах периода; задержка Kafka не меняет решение. Только CANCELED исключается из EXCLUDE и запроса занятости.
- Список Check-in: starts_at в `[from,to)` и статус EXPECTED/ARRIVING. По умолчанию — текущие сутки Europe/Moscow из конфига; CHECKED_IN/CANCELING/CANCELED и заезды с началом вчера не входят.
- Kafka key = booking_id, hash partitioner, раздельные consumer groups, чтение новых групп с oldest. Normal/error workers могут пересекаться: правильность обеспечивает идемпотентность и CAS. Доставка at-least-once; inbox не обещает exactly-once, счётчик ошибок не является DLQ или пределом повторов. Метрики копии не подключаются.

## Hotels и Review

- Каталог — сервис `hotels`; Hotel и Room — отдельные сущности. `review` знает только hotel_id и пользовательский рейтинг отеля. Рейтинга номера нет. Официальные звёзды (`stars`) не равны пользовательскому `rating`.
- `ListHotels`: стабильный order by id, limit по умолчанию 20, максимум 100; один batch RPC для всей непустой страницы. `Review.GetHotelRatings`: без произвольного ограничения числа ID, один `where hotel_id = any($1)` в своей БД, пустой список не обращается к storage. Нельзя делать N+1.
- Рейтинг представлен простым DTO `Rating`, устанавливается у сущности через `Hotel.SetRating` и читается через `Hotel.Rating`. DTO-обёртка `{Hotel *entity.Hotel; Rating Rating}` не нужна. GetHotel явно получает рейтинг по UUID и возвращает саму сущность; не оборачивай её в список ради последующего `[0]`. Список обогащается одним batch по UUID, без зависимости от порядка ответа Review. При отсутствии оценок rating отсутствует; оценка 0 с положительным review_count присутствует.
- `GetRoom/ListRooms` возвращают каталог и min/max без вызова Review. Booking обращается к Hotels до транзакции. Недоступность рейтингов не блокирует создание брони и CheckAvailability, а ошибка обогащения отелей передаётся наружу без выдуманного fallback.
- На этом этапе данные задаёт seed; нет CRUD каталога/оценок и новых Kafka-событий. Детали контрактов — [docs/hotels-review.md](docs/hotels-review.md).

## Идентификаторы и снимок номера

- Hotel, Booking, CheckIn, guest/actor, request, idempotency key и correlation-id используют UUID. Новые UUID создаются через `uuid.NewV4()`. В seed и примерах используются заранее сгенерированные UUID v4, без шаблонов `10000000-...` и кодирования смысла в UUID.
- Системный ID Room — положительный `int64`/PostgreSQL `bigint`; в API и Kafka он передаётся десятичной строкой (`"1"`). Источник ID — последовательность `public.rooms`; ID уникален во всём каталоге. Booking/Check-in сохраняют его как bigint. Шлюз передаёт строку напрямую; владельцы разбирают её локально через strconv, без новых общих helpers.
- `number` — отдельное обозначение номера внутри отеля (`"101"`), уникальное только в пределах hotel_id. Оно может совпадать у разных отелей и не используется для бронирования или GiST-проверки. `room_type` — строковое значение типа (`"Standard"`/`"Comfort"`/`"Family"`), без ID/отдельной сущности категории.
- Booking сохраняет room_number и room_type как снимок из Hotels при создании брони, без изменения версии и без дополнительного сетевого запроса. Источник актуального каталога остаётся Hotels. Replay возвращает исходный снимок и не обновляет его. Событие booking.confirmed.v1 передаёт room_id строкой, room_number и room_type; Check-in сохраняет этот снимок. События смены статуса идентифицируют бронь её UUID, без повторной загрузки каталога.
- booking_id и ключ Kafka — UUID брони, не room_id и не number. correlation-id — отдельный UUID идемпотентности события, стабильный при повторной доставке outbox. Исторические записи Kafka и отчёты о прежних прогонах не переписываются как новые результаты; актуальные контракты и исходные миграции меняются inplace.

## Notification

Notification подписан на booking.events.v1 отдельной consumer group notification-booking-events. Он обрабатывает booking.confirmed.v1, booking.activated.v1 и booking.canceled.v1; другие корректные события пропускает. Путь: Kafka subscriber → event router → отдельный use case события → infrastructure/gateway/push. Gateway-заглушка выводит структурированный JSON в stdout с русским заголовком и текстом, booking_id и correlation_id. Внешнего SMS/push-провайдера и регистрации устройств пока нет.

По решению пользователя здесь **нет inbox, БД, outbox, проекции и дедупликации**. Скопированный Kafka consumer подтверждает offset после успешного handler. Повторная доставка может повторить лог с тем же correlation-id; exactly-once не обещается. Новая consumer group читает с oldest. Ошибка handler не подтверждает сообщение; некорректное сообщение требует исправления/ручного решения, DLQ и пропуск ошибок автоматически не добавляются. Из RPC есть только Echo, также сохранены служебные healthcheck/reflection.

## PostgreSQL и ошибки

Booking, Check-in, Hotels и Review используют **четыре отдельных экземпляра PostgreSQL**, каждый со своим Deployment, Service, PVC и Secret. Адреса: booking-postgres:5432, check-in-postgres:5432, hotels-postgres:5432, review-postgres:5432. Все таблицы сервиса находятся в public; create/drop schema и схемы с именами сервисов не используются. Базы и SQL не разделяются между сервисами. Kafka общая. У API Gateway и Notification PostgreSQL нет.

Для нарушения бизнес-инварианта используй существующий NewBusinessErr: он возвращает FailedPrecondition (gRPC FailedPrecondition, HTTP 409). Новый Code Business не вводится. InvalidArgument (HTTP 422) — некорректные входные данные, Conflict (gRPC Aborted, HTTP 409) — CAS и конфликт ключа идемпотентности. Недопустимый статус, время заселения, длительность по условиям номера и пересечение брони — NewBusinessErr с явным русским пояснением. Не добавляй отдельные RoomUnavailable/DurationInvalid вместо этого конструктора. API Gateway передаёт ошибку владельца без своего бизнес-пакета.

## Оформление protobuf

Все локальные .proto оформляй через buf format: отступы в два пробела, отдельное поле на строке, пустые строки между логическими блоками. Русские комментарии объясняют RPC, сообщения, назначение полей, единицы измерения, форматы ID/времени, optional-семантику и асинхронные ответы. Не собирай весь контракт в сплошной блок. После изменения источника запускай Buf lint/build/generate и проверяй внешние клиенты; generated-файлы вручную не редактируй.

В Kafka-событиях используй явные имена: booking_id в envelope, booking_version для версии Booking; checkin_id/checkin_version в payload для CheckIn. Не используй aggregate_id/aggregate_version и безымянные id/version в wire-контракте. Не дублируй booking_id, request_id и версии между envelope и payload. correlation_id идентифицирует событие, causation_id — исходную команду, request_id — запрос для трассировки. Внутреннее API скопированного event/outbox не переименовывается.
