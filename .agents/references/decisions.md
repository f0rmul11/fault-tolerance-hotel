# Принятые решения и границы реализации

Правила находятся в репозитории HotelFlow. Первые две части соглашений приняты 11 октября 2026 года: архитектура, ошибки, unit-тесты, Go-стиль, ручной DI, хранение и логи.

## Модель от 12 октября 2026 года

Hotels владеет отдельными сущностями Hotel и Room, описанием отелей/номеров, официальными звёздами, координатами, удобствами и min/max длительности. Review владеет только пользовательскими рейтингами отелей; у номеров рейтинга нет. ListHotels/GetHotel обогащаются одним batch RPC в Review, который читает весь набор одним SQL. GetRoom/ListRooms не зависят от Review. Booking владеет гостем, номером, периодом и статусом брони, получает условия из Hotels до транзакции и проверяет занятость в своей БД. Отдельных сервисов Room, Search и Availability нет.

Period — VO [starts_at, ends_at), произвольное начало, UTC, точность до микросекунд. Одна бронь содержит один непрерывный период. Seed Hotels задаёт минимум 12 часов; максимум зависит от номера. Создание одной локальной транзакцией сохраняет CONFIRMED, ключ идемпотентности и outbox. Порядок в транзакции: проверка длительности, insert брони, outbox, commit. Ключ проверяется до вызова Hotels: сохранённый повтор возвращает бронь. При гонке вставок один запрос получает конфликт; advisory lock и повторное чтение ключа в confirm не нужны. Пересечения запрещает EXCLUDE USING gist по room_id и tstzrange; room lock и предварительное чтение пересечений не нужны. Подробности — `docs/booking.md`.

По указанию пользователя production-данных нет; модель и исходные миграции меняются inplace, без совместимости со старым форматом. Не сохраняй старые таблицы, proto-поля и события ради прежних учебных данных. Проверки выполняются на БД с актуальной схемой.

## Учебный этап

Сценарии: создание, чтение брони и проверка свободных номеров (API Gateway → Booking → Hotels). Пользователь выбрал одну локальную транзакцию и удаление Availability. Outbox сохраняется вместе с бронью; входящая идемпотентность включена по образцу module-2/transient-failures. UUID ключ передаётся клиентом и уникален в пределах гостя. Повтор с тем же номером и нормализованным периодом возвращает исходный результат; другой состав — Conflict. Ключ не имеет TTL и хранится с бронью. Ошибки до commit ключ не занимают. Автоматические RPC retry отложены; inbox включён для Booking/Check-in. Новая бронь сразу CONFIRMED версии 1; незавершённых сохраняемых состояний нет.

В бизнес-транзакции разрешена только собственная БД. Outbox relay имеет подтверждённое исключение: может держать свою транзакцию во время отправки Kafka.

## Актуальные правила и приоритет

Действующая спецификация — [HotelFlow 3.0](../../docs/specification.md), краткий контекст —
[agent-context.md](../../docs/agent-context.md). Они находятся в репозитории и переносятся вместе с кодом.
Спецификация 2.0 и первоначальный README курса сохранены как история; их архитектура,
общие контракты и перечень отсутствующих защит больше не являются требованиями.

Следующие решения **заменяют противоречащие старые формулировки спецификации и первой части правил**. Источники API/DDL — локальные proto и миграции сервисов. Архивные общие proto/SQL не регенерируются и не используются при разработке.

| Область | Действующее правило |
| --- | --- |
| SQL/DDL | SQL/DDL lower case. Разрешены primary key, unique и индексы. Для public.bookings разрешены EXCLUDE USING gist по room_id и tstzrange(starts_at, ends_at, '[)'), NOT NULL для room_id/starts_at/ends_at и CHECK конечного непустого периода. Это узкое исключение обеспечивает атомарный запрет пересечений. FK/references, каскады, триггеры и прочие ограничения вне разрешённого списка не добавляй. Условия длительности остаются в домене и Hotels. |
| Тесты | Основной новый набор — unit, читаемые table-driven где уместно. Реальные БД/брокеры, integration/E2E и coverage gate не обязательны; существующие проверки сохраняются |
| DI | internal/init.go + registry слоёв. Concrete imports допустимы для wiring registry; отдельные use case/service зависят от узких интерфейсов |
| Восстановление | DAO обязательно использует With(id, opts...Option), опции в option.go; гидратация не создаёт новых ID, событий и версий |
| DTO и коллекции | Методы разрешены. Именованные типы через type с методами заменяют повторяющиеся helper-функции; инварианты сущностей остаются в domain |
| Ошибки | Точная копия error.go/option.go ordererror с дополнительными Code; без своих полей/опций; русское пояснение; owner ErrorInterceptor и Clay proxy в gateway |
| Mapping | InvalidArgument → 422, FailedPrecondition → 409; Aborted → 409 уточняет старое OTHER → 500 |
| Go-стиль | Стандартные соглашения, gofmt, go vet, тесты; существующие библиотеки, узкие handwritten fakes по умолчанию |
| Логи | Структурированные log/slog, только значимые события, без спама и дублей по слоям |
| Метрики | Новые метрики пока не нужны; прежнее требование «/metrics нужны сразу» отменено. Существующие probes/lifecycle сохраняются |

Остальные рамки курса: шесть сервисов, минимальные сценарии, синтетические данные, реальное время через прямой time.Now() в use case и запрет чтения чужой БД. Gateway: Clay HTTP 200 для успешного ресурса и стандартный gRPC Status JSON для ошибки, без Problem.

## Детали по мере реализации

Общие правила ошибок, тестов, Go-стиля, DI и логов уже определены. Дополнительного одобрения на следование им не требуется.

- Сохранение пачки однотипных сущностей — variadic `Save(ctx, objects ...*entity.Type)`, один SQL, без отдельного `SaveMany`. CAS применяется к каждой записи; частичный успех означает ошибку и rollback общей транзакции.
- Версии xo/Goose/PostgreSQL, исполнитель миграций и изолированная БД codegen выбираются при первом storage с учётом окружения и фиксируются в Makefile/конфигурации.
- Конкретные ключи/индексы выбираются по идентичности и смыслу данных, а не добавляются автоматически во все таблицы.
- Политика повторов, dedup, порядка событий и дополнительные исключения технических таблиц решаются на соответствующем занятии.
- Дополнительные линтеры и mock-generators нужны только при конкретной пользе; начальный набор стандартный.

Текущая реализация и команды запуска: [бронирование](../../docs/booking.md). Proto-контракт принадлежит локальному `api` своего сервиса. Корневой общий protobuf удалён по прямому указанию пользователя; исключения для первого бронирования нет. Миграции и xo-шаблоны также остаются внутри сервиса.

У Booking локальный контракт `api/booking/booking/v1/booking.proto`: CreateBooking/GetBooking/CheckAvailability. У Hotels — ListHotels/GetHotel/GetRoom/ListRooms; у Review — GetHotelRatings. API Gateway сохраняет собственный публичный контракт. Генерация через Buf: local template создаёт API владельца, external template читает соседний `api` и пишет `internal/pkg/pb/external`. Booking имеет внешний Hotels-клиент, API Gateway — внешние Booking-, Check-in- и Hotels-клиенты. Gateway — транспортный прокси без use case и domain.

## Уточнения после первого code review

Эти требования заменяют прежние разрешения на компактную альтернативу outbox и необязательный business runtime:

- Booking разделяет статусы/перечисления (`types.go`), версию (`version.go`) и поведение сущности. Проверки состояния читаются по инвариантам, с отдельными понятными ошибками; без монолитной проверки всех полей.
- Каталога seed UUID в domain нет. `vo/selection.go` удаляется: существование номера и его условия определяет Hotels, занятость номера — Booking. Непустые ID и корректность проживания всё ещё проверяются.
- Входные структуры use case принадлежат его пакету, файлу `types.go`; общие DTO и сущности не содержат JSON-тегов.
- Роли — типизированные константы; policy выбирается interceptor по полному RPC method (HTTP middleware — по маршруту). Авторизация по роли не дублируется в use case. Владение ресурсом проверяет владелец данных.
- События собираются именно через `New(entity) pipe.Func[event.Events]`, `events.Base`, event payload и `event.Event`, затем `event.Buffer.Flush`. Контракт HotelFlow при этом сохраняется.
- Outbox и необходимые технические пакеты берутся из order-service; ранее написанный упрощённый relay заменяется. Допустимы адаптация импортов/конфигурации и локальные исправления конкретных дефектов. Новый альтернативный алгоритм не нужен.
- Composition root следует order-service: отдельный init для каждого слоя/компонента. Контроллеры всегда получают обязательные зависимости. Инициализация БД/producer может завершить старт ошибкой; nil-fallback и Echo-only режим больше не требуются.

Полный запуск проверяется на сконфигурированном стенде. Unit-тесты остаются без внешних сервисов; проверки старта реальных connectors отделяются от unit-тестов явно, без production-веток ради тестов.

Подробные правила API Gateway собраны в [одном документе](../skills/hotelflow-contracts-events/references/api-gateway.md). UUID брони — прямой uuid.NewV4(), без newID в DI. Error-пакет не хранит resource IDs/reason; их transport mapping описан в правилах ошибок.

## Check-in ↔ Booking: request/reply

Booking владеет бронью, её статусом и занятостью номера. Check-in владеет сущностью `CheckIn`: ожидаемым прибытием и его оформлением. Связь — `booking_id`; сущности Booking/Operation, копии статусов/версий Booking и сервисы `booking/request` в Check-in не нужны. Данные о госте, номере и периоде поступают из события создания для оформления заселения. Сервисы не читают чужую БД. Подробности — [Check-in](../../docs/check-in.md).

- Каждый RPC реализуется в отдельном файле `internal/app/<область>/v1/<метод>.go`. `service.go` содержит структуру и конструктор с конкретным `*usecase.Registry`. Не объявляй интерфейсы use case на уровне gRPC-хендлеров. В API Gateway остаются generated downstream-клиенты.
- UUID и response mapping находятся в самом методе, как в ad-service: `uuid.FromStringOrNil`, `lo.Map` либо простой цикл. Отдельные `parseID`, `bookingView`, `operationView`, `response.go` и универсальные мапперы не нужны. Обязательные ID проверяет use case/сущность; общую identity и роли — interceptor.
- Один use case на RPC **и один use case на сценарий входящего события**. Kafka-хендлеры вызывают именно use case. Вход — локальный `types.go`; optional поля — `mo.Option[T]`. Не создавай дополнительные use case для отдельных шагов одного сценария.
- `booking.confirmed.v1` регистрирует ожидаемое заселение. Check-in отправляет `checkin.arrival-requested.v1` или `checkin.cancellation-requested.v1`. Booking отвечает `booking.activated.v1` / `booking.canceled.v1` (пакеты `booking_activated` / `booking_canceled`); для бизнес-отказа — `booking.checkin-rejected.v1`. Обобщённого changed нет.
- **Ключ идемпотентности события — `correlation-id`**: один UUID создаётся при формировании события до записи outbox, сохраняется в `x-correlation-id` и `correlation_id` envelope. Relay при повторе не создаёт новый ID. Ответ — самостоятельное событие со своим ID; `causation_id` указывает ID запроса. HTTP `request_id` служит трассировке. Ни event_id, ни Kafka offset, ни request_id не подменяют ключ события.
- Подписчик проверяет заголовок и envelope, сохраняет inbox с этим correlation-id и только затем подтверждает offset. В inbox уникален `(correlation_id, topic)`. Реализация пакета inbox — копия payment-service с адаптацией импортов/форматирования; уникальность ключа усиливает DDL, не меняя алгоритм копии.
- Booking сохраняет CAS-переход и reply outbox одной транзакцией. Inbox может повторно вызвать use case после business commit: идемпотентность обеспечивает доменная логика, без AcceptEvent и отдельной таблицы обработанных событий. Повторная активация ACTIVE и отмена CANCELED не меняют состояние/версию; поздняя активация CANCELED не восстанавливает бронь. Reply допускается повторно: у него новый correlation_id и прежний causation_id, Check-in проверяет версию действия. Техническая ошибка возвращается inbox для retry.
- Check-in сохраняет HTTP-ключ `(actor_id, key)`, своё состояние и outbox одной транзакцией. `insert ... on conflict` и CAS обеспечивают конкуренцию без явных advisory/row locks в этом сценарии. Таблица requests — технические ключи, без отдельной сущности/жизненного цикла Operation. Повтор того же ключа и booking_id/action возвращает текущее состояние того же CheckIn, другой состав — Conflict.
- CheckIn: EXPECTED → ARRIVING → CHECKED_IN; отмена EXPECTED/CHECKED_IN → CANCELING → CANCELED. Ошибка Booking возвращает предыдущее состояние и русское пояснение. Ответ применяется только к ожидаемой версии собственного CheckIn; поздний ответ не меняет новое состояние. Это корреляция ответа и защита от устаревшего действия, не второй ключ дедупликации события.
- Booking: CONFIRMED → ACTIVE, отмена CONFIRMED/ACTIVE → CANCELED. Активация проверяет время исходного действия в пределах периода; задержка Kafka не меняет решение. Только CANCELED исключается из EXCLUDE и запроса занятости.
- Список Check-in: starts_at в `[from,to)` и статус EXPECTED/ARRIVING. По умолчанию — текущие сутки Europe/Moscow из конфига; CHECKED_IN/CANCELING/CANCELED и заезды с началом вчера не входят.
- Kafka key = booking_id, hash partitioner, раздельные consumer groups, чтение новых групп с oldest. Normal/error workers могут пересекаться: правильность обеспечивает идемпотентность и CAS. Доставка at-least-once; inbox не обещает exactly-once, счётчик ошибок не является DLQ или пределом повторов. Метрики копии не подключаются.

## Каталог и рейтинги (13 октября 2026)

Hotels владеет отдельными сущностями Hotel и Room, описанием отелей/номеров, официальными звёздами, координатами, удобствами и min/max длительности. Review владеет только пользовательскими рейтингами отелей; у номеров рейтинга нет. ListHotels/GetHotel обогащаются одним batch RPC в Review, который читает весь набор одним SQL. GetRoom/ListRooms не зависят от Review. Booking владеет гостем, номером, периодом и статусом брони, получает условия из Hotels до транзакции и проверяет занятость в своей БД. Отдельных сервисов Room, Search и Availability нет.

Review в этом шаге только читает учебные оценки отелей. У номеров рейтинга нет. Публичный каталог проксируется через Clay, условия бронирования не зависят от Review. Подробности: [Hotels и Review](../../docs/hotels-review.md).

### Уточнение обогащения рейтинга

Review.GetHotelRatings не ограничивает batch произвольным числом 100. DTO Rating содержит только значение и число оценок. Use case GetHotel получает рейтинг по UUID, вызывает Hotel.SetRating и возвращает сам Hotel. DTO Hotel с вложенной сущностью и рейтинговым полем удалён; одиночный результат не извлекается из массива. Список сохраняет один batch-запрос и устанавливает рейтинги тем же методом сущности. Рейтинг не сохраняется в БД Hotels.

## Идентификаторы и снимок номера

- Hotel, Booking, CheckIn, guest/actor, request, idempotency key и correlation-id используют UUID. Новые UUID создаются через `uuid.NewV4()`. В seed и примерах используются заранее сгенерированные UUID v4, без шаблонов `10000000-...` и кодирования смысла в UUID.
- Системный ID Room — положительный `int64`/PostgreSQL `bigint`; в API и Kafka он передаётся десятичной строкой (`"1"`). Источник ID — последовательность `public.rooms`; ID уникален во всём каталоге. Booking/Check-in сохраняют его как bigint. Шлюз передаёт строку напрямую; владельцы разбирают её локально через strconv, без новых общих helpers.
- `number` — отдельное обозначение номера внутри отеля (`"101"`), уникальное только в пределах hotel_id. Оно может совпадать у разных отелей и не используется для бронирования или GiST-проверки. `room_type` — строковое значение типа (`"Standard"`/`"Comfort"`/`"Family"`), без ID/отдельной сущности категории.
- Booking сохраняет room_number и room_type как снимок из Hotels при создании брони, без изменения версии и без дополнительного сетевого запроса. Источник актуального каталога остаётся Hotels. Replay возвращает исходный снимок и не обновляет его. Событие booking.confirmed.v1 передаёт room_id строкой, room_number и room_type; Check-in сохраняет этот снимок. События смены статуса идентифицируют бронь её UUID, без повторной загрузки каталога.
- booking_id и ключ Kafka — UUID брони, не room_id и не number. correlation-id — отдельный UUID идемпотентности события, стабильный при повторной доставке outbox. Исторические записи Kafka и отчёты о прежних прогонах не переписываются как новые результаты; актуальные контракты и исходные миграции меняются inplace.

## Notification

Notification подписан на booking.events.v1 отдельной consumer group notification-booking-events. Он обрабатывает booking.confirmed.v1, booking.activated.v1 и booking.canceled.v1; другие корректные события пропускает. Путь: Kafka subscriber → event router → отдельный use case события → infrastructure/gateway/push. Gateway-заглушка выводит структурированный JSON в stdout с русским заголовком и текстом, booking_id и correlation_id. Внешнего SMS/push-провайдера и регистрации устройств пока нет.

По решению пользователя здесь **нет inbox, БД, outbox, проекции и дедупликации**. Скопированный Kafka consumer подтверждает offset после успешного handler. Повторная доставка может повторить лог с тем же correlation-id; exactly-once не обещается. Новая consumer group читает с oldest. Ошибка handler не подтверждает сообщение; некорректное сообщение требует исправления/ручного решения, DLQ и пропуск ошибок автоматически не добавляются. Из RPC есть только Echo, также сохранены служебные healthcheck/reflection.

## PostgreSQL и ошибки

Booking, Check-in, Hotels и Review используют **четыре отдельных экземпляра PostgreSQL**, каждый со своим Deployment, Service, PVC и Secret. Адреса: booking-postgres:5432, check-in-postgres:5432, hotels-postgres:5432, review-postgres:5432. Все таблицы сервиса находятся в public; create/drop schema и схемы с именами сервисов не используются. Базы и SQL не разделяются между сервисами. Kafka общая. У API Gateway и Notification PostgreSQL нет.

Для нарушения бизнес-инварианта используй существующий NewBusinessErr: он возвращает FailedPrecondition (gRPC FailedPrecondition, HTTP 409). Новый Code Business не вводится. InvalidArgument (HTTP 422) — некорректные входные данные, Conflict (gRPC Aborted, HTTP 409) — CAS и конфликт ключа идемпотентности. Недопустимый статус, время заселения, длительность по условиям номера и пересечение брони — NewBusinessErr с явным русским пояснением. Не добавляй отдельные RoomUnavailable/DurationInvalid вместо этого конструктора. API Gateway передаёт ошибку владельца без своего бизнес-пакета.
