# Транзакции и версия

## Абстракция транзакции

Используй сервисный пакет `internal/pkg/transaction` с API образца:

```go
err := transaction.Exec(ctx, func(txCtx context.Context) error {
    if err := bookingStorage.Save(txCtx, booking); err != nil {
        return err
    }
    return anotherStorage.Save(txCtx, anotherEntity)
})
```

Вызывай `transaction.Exec` напрямую. Не добавляй в use case/service поле `exec`, функцию-исполнитель или интерфейс транзакции ради DI. В тестах подменяй executor через существующий `transaction/abstract`, без дополнительных зависимостей бизнес-компонента.

Это эскиз API, а не уже существующие методы HotelFlow. Use case определяет границу бизнес-транзакции. Внутренний service может участвовать в ней через переданный контекст; не открывай независимую транзакцию внутри него для части того же сценария. В use case/service нет SQL, `pgx.Tx`, `Begin`, `Commit`, `Rollback` или driver-specific options.

Обязательное поведение пакета при переносе:

- `Exec(ctx, callback)` передаёт транзакционный `txCtx`; **все** обращения к storage внутри callback используют его.
- Storage использует `wrapper.Pool(ctx)`: вне транзакции — pool; внутри — один lazily initialized transaction executor.
- `nil` от callback приводит к commit; ошибка — к rollback. Ошибка commit возвращается вызывающему. После panic выполняется rollback, затем исходный panic пробрасывается дальше. После rollback изменённый объект в памяти не становится автоматически прежним: не переиспользуй его как сохранённый результат.
- Вложенный `Exec` присоединяется к текущей транзакции, не создаёт savepoint или независимый commit. Ошибку внутреннего действия необходимо вернуть наружу, а не поглотить.
- Один контекст транзакции — один pool собственной БД и последовательные операции. Не смешивай pool разных БД и goroutine, использующие один pgx transaction.
- Контекст запроса и ошибки сохраняются; cleanup должен действительно освободить транзакцию также при отменённом запросе. Подтверждение успеха даётся только после успешного commit.

Внутри **бизнес-транзакции** запрещены gateway/RPC/HTTP/Kafka и другие внешние системы. Данные извне получай до неё, сетевые действия выполняй после её завершения. Локальная транзакция не делает последовательность межсервисных вызовов атомарной.

**Разрешённое исключение:** пользователь отдельно разрешил outbox relay держать собственную транзакцию БД во время отправки Kafka, как в исходном пакете. Это не разрешает вызывать Kafka из use case внутри транзакции, сохраняющей бронь.

## Что исправить при переносе transaction

Источник — `ad-service/internal/pkg/transaction`, включая `abstract` и `wrapper`. Переносить после проверки, не копировать слепо:

1. `Exec` передаёт nil args, а ad-service `wrapper/database.go` делает безусловное `tx.Args().(*pgx.TxOptions)`. При nil нужен default; в order-service это уже проверяется.
2. Обе версии `Exec` вызывают deferred `commit(err)` и не обрабатывают panic. Если callback паникует, именованный err может остаться nil и записи закоммитятся. Исправь эту ветку перед использованием.
3. Контекст образца не различает pool. Сохрани ограничение одного pool; не обещай транзакцию нескольких хранилищ разных сервисов.

Минимальная проверка переноса: успешный callback, ошибка после первой записи, panic после первой записи, ошибка commit, вложенный Exec и nil options. Пакет уже используется в runtime HotelFlow; сохраняй проверенные исправления при переносе других частей образца.

## Версия внутри сущности

Сохрани подход пользователя, закрытый в `domain/entity`:

```go
type version struct {
    Old int
    new *int
}

func (v *version) inc() {
    v.new = lo.ToPtr(v.Old + 1)
}
```

У сущности закрытое поле `version`; getters `OldVersion()` и `Version()` возвращают исходную и текущую версии. Текущая — `*new`, если задана, иначе `Old`. Восстановление из БД устанавливает `Old` и `new=nil`. Начальная версия новой сущности — 1 согласно спецификации. Преобразование SQL bigint в выбранный Go-тип проверяется на допустимость.

`inc()` вызывается только успешными доменными методами изменения сохраняемого состояния. Use case, storage, DTO, mapper и gateway не увеличивают версию. Неудачная проверка, чтение, восстановление и обогащение ответа версию не меняют.

Повторные `inc()` над одним загруженным экземпляром оставляют **Old+1**, а не Old+2. Это одна новая версия состояния, предназначенного для одного сохранения. Сформируй финальное состояние, сохрани экземпляр один раз и после завершения работы откажись от него; для следующего отдельного изменения перечитай сущность. Нельзя преждевременно передвигать Old до успешного commit или вызывать inc из storage для обхода stale version.

Пользователь разрешил CAS при необходимости. Создание одной строки CONFIRMED использует версию 1; CAS используется при активации и отмене существующей брони. Реализация версии находится в `version.go` пакета сущности.

## CAS

```sql
update public.bookings
set status = $1, version = $2
where id = $3 and version = $4;
```

Параметры поступают из entity: новый статус, `Version()`, `ID()`, `OldVersion()`. SQL не рассчитывает версию вместо доменного метода. Обновление выполняется в локальной транзакции: ровно одна изменённая строка — ожидаемый результат; ноль — CAS conflict; более одной — ошибка целостности и rollback. PK/UNIQUE теперь разрешены, но их наличие не гарантируется для любой таблицы; корректность критерия записи и RowsAffected остаётся обязанностью storage. Автоматического retry конфликта это правило не вводит.

Period — VO [starts_at, ends_at), произвольное начало, UTC, точность до микросекунд. Одна бронь содержит один непрерывный период. Seed Hotels задаёт минимум 12 часов; максимум зависит от номера. Создание одной локальной транзакцией сохраняет CONFIRMED, ключ идемпотентности и outbox. Порядок в транзакции: проверка длительности, insert брони, outbox, commit. Ключ проверяется до вызова Hotels: сохранённый повтор возвращает бронь. При гонке вставок один запрос получает конфликт; advisory lock и повторное чтение ключа в confirm не нужны. Пересечения запрещает EXCLUDE USING gist по room_id и tstzrange; room lock и предварительное чтение пересечений не нужны. Подробности — `docs/booking.md`.

Проверка ключа до Hotels возвращает сохранённую бронь для повтора. Конкурирующие INSERT разрешает уникальность в БД: проигравший получает Conflict. Не сериализуй повторы advisory lock и не перечитывай ключ в confirm. Сохраняй ключ в той же записи, что и бронь, с unique (guest_id, idempotency_key); insert использует on conflict do nothing с проверкой RowsAffected, как в module-2. Отдельная таблица незавершённых операций не нужна. Ошибка commit означает неизвестный ответ клиенту, но не частично сохранённую бронь; клиент повторяет тот же состав и ключ.

Для отмены брони предикат EXCLUDE и запроса занятости одинаков: `status is distinct from 'CANCELED'`. Reply outbox сохраняется вместе с CAS-переходом Booking. Повторную обработку разрешает inbox, доменные методы не повторяют переход и увеличение версии. Отдельная таблица обработанных событий и AcceptEvent не нужны. У Check-in собственное состояние, HTTP-ключ и outbox сохраняются одной транзакцией; reply проверяет ожидаемую версию CheckIn. Явные advisory/row locks и таблица жизненного цикла операций в Check-in не нужны.
