# Storage и SQL HotelFlow

## Хранилища и DAO

1. Размещай storage каждой сущности/агрегата в `internal/infrastructure/storage/<сущность>`, DAO — в его `dao/`. API выражает необходимую операцию и возвращает сущность, коллекцию или внутренний DTO; SQL/pgx/xo не видны use case.
2. DAO **встраивает соответствующую сгенерированную xo-структуру**, как `type Booking struct { xo.Booking }`. Имя xo-типа определяется фактической генерацией. Не подменяй xo вручную написанной копией.
3. DAO обязательно восстанавливает entity через `With(id, opts ...Option)` с опциями из `option.go`: ID, все сохранённые поля, статус, версия и даты. Пример использует `ConvertTo`: простое преобразование полей и `With/Option` без повторной полной валидации сохранённой сущности. Не добавляй `validateColumns` и каталог проверок SQL-полей в DAO. Не заменять гидратацию `New...` или бизнес-методами. Для записи получай значения через getters домена.
4. Generated xo размещается в `internal/pkg/xo`; SQL-структуры существуют только внутри storage. Для составной выборки допускается DAO с embedded xo и полями проекции. Чтение брони возвращает одну строку с starts_at/ends_at; DAO создаёт Period и восстанавливает Booking через With/Option. Не добавляй массивы, группировки и коллекции для одной брони. Не заставляй произвольную аналитическую проекцию притворяться полноценной сущностью.
5. Пиши нативный параметризованный SQL без ORM/query builder: keywords и обычные идентификаторы в lower case (`select`, `insert into`, `update`, `where`). Используй scany/pgxscan с executor из `wrapper.Pool(ctx)`. Не вызывай исходный pool напрямую, обходя текущую транзакцию. Имена столбцов и разрешённая сортировка контролируются кодом; значения не конкатенируются в SQL. Регистр строковых значений вроде `'CONFIRMED'` не меняй.
6. Обрабатывай not found и CAS-конфликт на месте. Остальные ошибки SQL передавай напрямую либо с контекстом через `%w`; не создавай универсальный классификатор `storageError` с каталогом SQLSTATE и сетевых ошибок. Неизвестную техническую ошибку существующий ErrorInterceptor превращает в безопасный русский Internal; отмена и deadline сохраняются. Текст SQL и pgx-типы не передавай наружу как публичный контракт ошибки.
7. Nullable xo-поля преобразуй напрямую существующими SQL/UUID-типами. Не создавай отдельные `nullableID`/`nullableText` и похожие helpers ради элементарного преобразования. Не дублируй доменные проверки отдельной проверкой каждого `Valid`. Обязательность в приложении не означает NOT NULL в DDL, кроме явно разрешённых границ периода и room_id. При появлении точных чисел не преобразуй их через float64.
8. Для операции над одной сохранённой сущностью проверяй ровно одну затронутую строку уже в исходной версии, не только после внедрения CAS. Ноль — отсутствие ожидаемой записи, больше одной — ошибка целостности и rollback локальной транзакции. Это проверка результата записи без сравнения version; она не предотвращает учебные гонки read–check–write. Для намеренной batch-операции ожидаемое число строк задаётся её контрактом.

9. Пакетное сохранение называй `Save(ctx, objects ...*entity.Type)`: тот же метод принимает одну сущность или несколько. Вызов коллекции — `storage.Save(ctx, objects...)`. Не вводи отдельный `SaveMany` и не скрывай внутри цикл одиночных SQL. Выполняй один batch SQL; в CAS сравнивай старую версию каждой записи и проверяй число обновлённых строк. Ошибка хотя бы одной записи возвращается наружу, общая бизнес-транзакция откатывает весь набор и связанные записи outbox. Пустой набор — no-op.

Один SQL-запрос выполняй напрямую. Не создавай отдельную бизнес-транзакцию или метод-обёртку вроде `savePending` только вокруг одного `storage.Create`. Для атомарного изменения состояния и записи outbox транзакция обязательна.

Для границ транзакции и точного протокола версии прочитай [transactions.md](references/transactions.md).

Требования xo/With относятся к storage доменных сущностей. В скопированном техническом outbox сохраняй DAO образца; не перестраивай пакет ради генератора.

## Миграции и xo

- SQL находится в `tools/migrations/<timestamp>_<описание>.sql`, используется формат Goose с `-- +goose Up` и `-- +goose Down`; StatementBegin/StatementEnd — для многооператорных конструкций, которым это требуется. Одна миграция — одно связное изменение схемы.
- Текущий этап — без production-данных и требований совместимости: пользователь разрешил inplace. Переписывай исходную миграцию под актуальную модель, не добавляй legacy-таблицы и перенос старого формата. Down удаляет созданные этой миграцией таблицы. При появлении требований сохранности данных правила миграции необходимо пересмотреть.
- SQL/DDL lower case. Разрешены primary key, unique и индексы. Для public.bookings разрешены EXCLUDE USING gist по room_id и tstzrange(starts_at, ends_at, '[)'), NOT NULL для room_id/starts_at/ends_at и CHECK конечного непустого периода. Это узкое исключение обеспечивает атомарный запрет пересечений. FK/references, каскады, триггеры и прочие ограничения вне разрешённого списка не добавляй. Условия длительности остаются в домене и Hotels.
- PK/UNIQUE разрешены, но это не команда автоматически добавить их во все таблицы. Выбирай ключи по идентичности и смыслу данных; Для текущего создания брони unique по гостю и ключу идемпотентности обязателен. UNIQUE nullable-колонки не заменяет проверку обязательности в приложении.
- Миграции, генерация и storage работают только с БД/схемой своего сервиса. В deployment выбирай явного исполнителя миграций; не добавляй запуск каждым replica без решения о порядке.
- `tools/xo_templates` задаёт необходимый формат xo. Генерируй на изолированной БД с применёнными миграциями. Проверь фактический вывод для выбранных ключей и nullable-типов; если таблица без PK, генератор должен поддерживать и её.
- Зафиксируй версию xo и используемых шаблонов; не копируй `@latest`. DSN должен учитывать конфигурацию хоста/порта/БД и не попадать с паролем в логи. Время записи поступает из принятого источника времени, а не скрытого `time.Now()` внутри xo helper.
- Подготовка БД, `migrations-up`, явный destructive reset и генерация должны иметь различимые команды. Не копируй цель `migrations: migrations-reset migrations-up`; обычная генерация не сбрасывает данные. Не использовать `-allow-missing` как стандартное скрытие пропусков миграций.
- В HotelFlow доступны корневые `migrate-booking`, `migrate-hotels`, `xo-booking`, `xo-hotels`; DSN задаётся явно. Outbox runtime копируется из order-service, его актуальная схема задаётся исходной миграцией без перехода со старого формата.

## Проверка изменения

Основные новые тесты — unit: DAO → entity, сохранённые поля/версия, nullable/невалидные данные, mapping ошибок и RowsAffected с подменой executor. Транзакционную обёртку проверяй через тестовый transaction executor: commit, rollback и panic. Unit-тест не доказывает корректность SQL или миграции в настоящем PostgreSQL; отдельно указывай, что фактически проверено. Генерация xo при первом подключении остаётся отдельной технической проверкой. Integration/E2E с БД не являются обязательным набором для каждой задачи и добавляются при отдельной необходимости. При внедрении CAS проверь stale version; до этого не меняй ожидания учебных гонок на защищённое поведение.

## EXCLUDE и генерация моделей

GiST с btree_gist запрещает пересечения одного номера на уровне PostgreSQL, включая прямые INSERT/UPDATE. Соседние периоды разрешены за счёт [). SQLSTATE 23P01 по bookings_room_period_excl отображается в NewBusinessErr (FailedPrecondition); 40P01 — в Conflict с предложением повторить тот же ключ. Автоматический retry не добавляй. Проверка доступности является снимком, а не гарантией будущей записи.

`make booking-tools` устанавливает закреплённый xo с узким patch для expression-index: он пропускает такие индексы при генерации row-моделей. Не удаляй EXCLUDE из БД ради xo. `make xo-booking` читает мигрированную БД, не меняет схему и не сбрасывает данные.

## Изоляция PostgreSQL

У каждого владельца данных свой PostgreSQL: Booking, Check-in, Hotels, Review. Все таблицы в public; схемы с именами сервисов не создаются. Gateway и Notification работают без БД. Миграции выполняются в своей базе; xo генерирует только перечисленные в tools/xo.yaml модели из public. Kafka общая.

## Оформление запросов

SQL в storage оформляй многострочными raw string: нижний регистр, табы для вложенности, отдельные строки для select/from/where/join/order by/limit, условий and/or, колонок insert/update и аргументов batch unnest. Длинный запрос объявляй локальной константой рядом с методом, а не внутри вызова Exec/Query. Не выравнивай SQL случайной смесью пробелов и табов. При форматировании сохраняй операции, порядок параметров, условия, сортировку и ограничения. Правило относится и к storage inbox/outbox.
