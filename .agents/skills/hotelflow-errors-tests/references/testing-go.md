# Unit-тесты и Go-стиль

## Что проверять

Новые автоматические проверки бизнес-логики — unit-тесты рядом с кодом в `*_test.go`. Для однотипных случаев используй `tests := []struct{...}` и `t.Run` с понятным именем. В кейсе видны вход, существенная подготовка и ожидаемый результат. Разные по устройству сценарии проверяй отдельными тестами, не делай огромную таблицу с десятками опциональных функций.

| Объект проверки | Значимые случаи |
| --- | --- |
| Entity / VO | Успешные и запрещённые переходы, границы дат, инварианты, сохранение состояния/версии после отказа |
| DAO | With/Option восстанавливает ID, статус, даты, все поля и OldVersion; нет новых ID/событий; ошибки доменных инвариантов сохраняются. Отдельная проверка каждого nullable-флага не требуется |
| Use case | Happy path, известный отказ, техническая ошибка и неизвестный outcome; сохранённое состояние, значимые обращения к портам, отсутствие недопустимого следующего шага |
| Gateway / handler | DTO mapping, передача context/metadata, известный статус зависимости, русский безопасный ответ |
| Event converter | Snapshot соответствует состоянию, полный envelope, стабильные ID, последующее изменение entity не меняет собранное событие |
| Transaction abstraction | Commit/rollback, ошибка commit, panic, nil options, вложенное выполнение на тестовом executor |

Не тестируй getters, строку SQL или wiring точным повторением реализации ради процента покрытия. Для storage unit-тест может проверить параметры executor, ошибки и RowsAffected; он не доказывает, что запрос исполняется в PostgreSQL. Не называй fake transaction доказательством реальной атомарности БД.

Первое бронирование проверяется на успешном результате, известном отсутствии мест, ошибке сохранения, потерянном ответе commit и конкурентных повторах ключа. Тест проверяет атомарное сохранение в outbox; автоматический RPC retry и compensation всё ещё не реализованы. Успех фиксируется только после предусмотренного сохранения; после ошибки сохранения нельзя выдавать подтверждение и событие успеха. Детерминированно воспроизводимый учебный дефект допустимо описать отдельным тестом/примером, но не добавляй случайно падающий concurrency-тест в обязательный suite.

## Инструменты и изоляция

- Стандартный набор — `testing`, `httptest`, `t.Helper`, `t.Cleanup`, `t.Setenv`, `t.TempDir`. `httptest.NewRecorder` и fake handler не требуют внешнего сервиса. Существующую библиотеку assertions можно использовать, если она уже выбрана модулем; новая библиотека не обязательна.
- Подменяй узкие порты handwritten fake/stub. Generated mock нужен только когда упрощает сложное взаимодействие; фиксируй версию генератора и не правь generated mock вручную. Наличие библиотеки в go.sum ещё не означает, что она выбрана прямой зависимостью.
- Mock-проверки касаются значимого порядка и эффектов: например, после неуспешной записи нет вызова publish. Не привязывай тест к каждому getter, несущественному порядку чтений и внутренним private helper.
- Ответы зависимостей управляемы; нет time.Sleep для проверки обычной логики. В use case не внедряются часы через поля и конструкторы: используется time.Now(). В доменных тестах передавай готовое время методам сущностей; время сценария проверяй по допустимому диапазону, без точного сравнения с заранее заданной датой. UUID брони создаётся прямым uuid.NewV4(), без newID-поля/параметра ради теста. Проверяй непустой ID и его связь с эффектами; не требуй заранее заданного UUID. Ошибку генерации не игнорируй.
- `t.Parallel` только для независимых кейсов без общего mutable state, env или глобальной конфигурации. У каждого кейса собственные сущности и fake; изменённое состояние не протекает между кейсами.
- Код ошибки проверяй как typed category/reason/status. Точный русский текст проверяй там, где тестируется публичный контракт сообщения; не делай всю тестовую базу зависимой от каждой формулировки.
- PostgreSQL/Kafka/Docker и integration/E2E-фреймворки не входят в обязательный набор новых unit-тестов. Уже существующие проверки сохраняются. Проверки реальных миграций/генерации или среды выполняются отдельно по необходимости, с честным указанием границ проверки.

## Обычный Go-стиль

- Правила оформления относятся ко всему написанному вручную Go-коду шести сервисов и `hotelctl`, включая технические пакеты и тесты. Generated-файлы не редактируй вручную.
- Непустое тело функции всегда оформляй на нескольких строках: открывающая скобка, операторы с отступом и закрывающая скобка. Это относится и к однострочным getters, конструкторам Option, вложенным и анонимным функциям. Не объединяй самостоятельные операторы через `;`; отделяй объявления и логические шаги пустыми строками.
- Составные литералы структур и map с несколькими полями раскрывай по одному полю на строку. Длинные вызовы конструкторов и вложенные инициализации разбивай по аргументам, чтобы зависимости и значения читались отдельно.
- Отступы — табы в стандартном формате Go; затем применяй gofmt и goimports. Их успешный запуск не доказывает читаемость: они сохраняют часть сжатых однострочных тел, поэтому сначала расставь переносы строк. Импорты организованы без ручного выравнивания.
- Имена понятные, package names короткие и lower case; придерживайся существующего layout, не переименовывай всё ради стиля. Для новых обычных package names избегай underscores, file names могут быть snake_case.
- `ID`, `HTTP`, `URL`, `SQL` сохраняют общепринятое написание в идентификаторах. Receiver короткий и соответствует типу. Никаких I-приставок у интерфейсов и универсальных названий utils/common для бизнес-логики.
- Конструктор — `New` или `New<Type>`, возвращает конкретный тип; `error` добавляется, если создание реально может завершиться ошибкой. `With(id, opts ...Option)` — отдельный конструктор восстановления, как закреплено пользователем. Не создавай сеть, глобальные singleton или фоновые goroutine в constructor use case.
- `context.Context` — первым аргументом операций, которым нужны отмена/metadata. Передавай входной context дальше; внутри бизнес-запроса не подменяй его Background и не храни в сущности. Cleanup/lifecycle может иметь отдельный контекст по своей задаче.
- Ранний возврат ошибок, `%w`, errors.Is/As; не игнорируй ошибки, не используй panic для ожидаемого бизнес-отказа. Язык публичного сообщения регулируется отдельным правилом, технические имена не переводятся.
- Интерфейсы узкие и определены у потребителя. Нет интерфейса на каждый struct ради формальности, универсального repository или generic framework без текущей необходимости.
- Используй стандартную библиотеку и уже выбранные зависимости. В одном модуле не добавляй вторую библиотеку UUID/ошибок/логов для той же задачи. Новая зависимость оправдывается конкретной потребностью, версия фиксируется; не копируй весь go.mod/Makefile образца.

## Команды проверки

Из затронутого Go-модуля: `go vet ./...` и `go test -race ./...` либо существующий make test. Перед ними форматируй изменённые Go-файлы. В HotelFlow `make -C services/<service> test` уже выполняет race-тесты, включая существующие lifecycle-проверки с subprocess/TCP; это не название отдельного unit-only target.

Go lint framework сейчас не настроен; первоначально достаточно gofmt, go vet и тестов. Не вводи обязательный golangci-lint, порог покрытия или большой набор линтеров в этой задаче. Buf lint относится к protobuf; после изменения API запускай генерацию затронутых контрактов.

Запускай проверки соразмерно изменению. При правке только инструкций достаточно проверки их формата, ссылок и согласованности; runtime-тесты не нужны. В итоговом сообщении указывай фактически выполненные команды и ограничения среды, не называя непроверенный SQL/интеграцию исправными.

Проверки ролей тестируются таблицей interceptor/middleware: полный RPC method или HTTP route, роль, требуемый actor/request_id, ожидаемый код, факт вызова handler. Отдельно проверь, что обход публичного HTTP через прямой gRPC не обходит policy.
