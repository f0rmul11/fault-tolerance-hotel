# Ошибки, тесты и качество Go-кода

При изменении ошибок или API прочитай [ошибки и транспорт](references/errors.md). При написании Go-кода и проверок прочитай [unit-тесты и Go-стиль](references/testing-go.md). Ручной DI через init и registry описан в [архитектуре](../hotelflow-domain-usecase/references/architecture.md).

## Обязательный результат

- Пользователь получает корректный gRPC/HTTP-код и понятное пояснение на русском. Машинный code не зависит от текста. Ошибка зависимости, потерянный ответ и известный бизнес-отказ различаются.
- Ошибки владельцев копируют `ordererror` точно, разрешены только дополнительные Code. Семантика cause/WithBase/BaseMessage сохраняется как в образце. ErrorInterceptor установлен у владельцев; API Gateway следует правилам Clay proxy без собственного пакета ошибок.
- Новая логика проверяется unit-тестами с подменой узких портов. Таблица применяется к однотипным вариантам. Тесты не требуют внешних БД/брокеров и не заставляют реализовать CAS/outbox/retry раньше занятия.
- DI выполняется через init и registry, сущности восстанавливаются через With/Option; тесты могут создавать компоненты напрямую через те же конструкторы.
- Go-код форматируется, проходит согласованные проверки затронутого модуля. Не вводятся новые framework, линтеры и mock-generators без конкретной необходимости.

## Логирование

Используй существующий `log/slog` с постоянным текстом сообщения и отдельными атрибутами. На старте настрой структурированный handler, предпочтительно JSON для стенда; не прячь поля в `fmt.Sprintf`. Пример формы: `slog.ErrorContext(ctx, "Не удалось сохранить бронь", "request_id", requestID, "booking_id", bookingID, "operation", "create_booking", "error", err)`.

- Info — старт/остановка, значимый итог сценария или изменение состояния, нужное для разбора эксперимента. Не логируй каждое чтение, вызов getter, SQL и промежуточный шаг.
- Error — неожиданный технический сбой, с контекстом операции. Обычный отказ валидации, отсутствие номера или ожидаемый конфликт не требуют Error; Warn нужен, когда событие действительно требует внимания оператора.
- Ошибка логируется один раз на выбранной границе обработки запроса/сообщения. Остальные слои возвращают ошибку с cause. Domain не логирует. На разных сервисах допустим собственный итог их операции с тем же request_id; внутри одного сервиса не дублируй одну ошибку на каждом слое.
- Передавай request_id, имя операции, стабильный code и известный aggregate ID; длительность добавляй там, где она помогает диагностике. Не подставляй выдуманные ID при неизвестном результате.
- Не записывай полные payload, секреты, DSN с паролем и персональные данные. Техническая cause может содержать англоязычный текст в диагностике; пользовательское Message/detail остаётся русским и безопасным.
- Не включай обязательный request/response dump, SQL trace и шумный polling-log. Повторяющиеся технические ошибки фонового worker должны логироваться с ограниченной частотой/агрегацией; это не retry-политика и не новая бизнес-защита.
- **Метрики пока не нужны:** не добавляй counters/histograms, `/metrics`, exporters, dashboards или outbox.WithMetrics. Не удаляй существующие probes/lifecycle и уже имеющуюся инфраструктуру без задачи на это. Старое требование спецификации о новых базовых метриках отменено текущим решением пользователя.

При завершении укажи, какие unit-тесты и команды выполнены. Отделяй проверку логики на fake от проверки SQL/сети на настоящей системе; не заявляй интеграционные гарантии по результатам unit-теста.

При правке общего подхода проверяй все шесть сервисов HotelFlow, включая повторяющиеся error/interceptor/logging пакеты каркасов. Отмечай, какие требования неприменимы без бизнес-сценариев; не добавляй отсутствующие слои только ради одинаковой структуры.
