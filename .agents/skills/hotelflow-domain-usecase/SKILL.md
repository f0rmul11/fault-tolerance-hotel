# Домен и сценарии HotelFlow

Перед работой прочитай [архитектурные правила](references/architecture.md). Они определяют размещение типов, границы зависимостей, инкапсуляцию и роль каждого слоя.

Hotels владеет отдельными сущностями Hotel и Room, описанием отелей/номеров, официальными звёздами, координатами, удобствами и min/max длительности. Review владеет только пользовательскими рейтингами отелей; у номеров рейтинга нет. ListHotels/GetHotel обогащаются одним batch RPC в Review, который читает весь набор одним SQL. GetRoom/ListRooms не зависят от Review. Booking владеет гостем, номером, периодом и статусом брони, получает условия из Hotels до транзакции и проверяет занятость в своей БД. Отдельных сервисов Room, Search и Availability нет.

## Порядок работы

1. Определи один сценарий и сервис-владелец данных. Сверь состояние и переходы с актуальной спецификацией, указанной в корневом AGENTS.md через документ решений.
2. Найди сущность/агрегат, отвечающий за каждое бизнес-правило. Реализуй правило доменным методом; состояние не меняется прямым присваиванием из use case, storage или handler.
3. Создай use case в `internal/application/usecase/<область>/<сценарий>` с типом `UseCase` в `usecase.go`. Это правило для сервисов-владельцев; API Gateway не содержит use case. Use case владельца загружает данные через интерфейсы, вызывает доменные методы, сохраняет результат и организует внешние шаги. Один бизнес-сценарий может иметь HTTP- и gRPC-вход, которые вызывают один use case.
4. Выделяй узкий `internal/application/service` только для конкретной прикладной задачи сценария: обогащение, получение данных из нескольких источников, подготовка результата. Не переносить туда инварианты сущностей или весь сценарий.
5. В транспортном адаптере оставь разбор запроса и преобразования. Общие проверки контекста и ролей выполняй в interceptor по полному RPC method (на HTTP — в middleware по маршруту), с именованным типом роли и константами. Use case не дублирует role allow-list; проверяет владение ресурсом и доменные правила. Инварианты должны проверяться также при вызове use case из другого транспорта или consumer.
6. Объявляй узкие интерфейсы storage/gateway рядом с потребителем в use case или service. Собирай компоненты через `registry.go` слоёв, которыми управляет `internal/init.go`. Concrete infrastructure разрешён в registry для wiring; отдельный use case/service получает только необходимые порты и не хранит весь registry.
7. Для записи или транзакции используй навык `hotelflow-storage`; для изменения внешнего контракта, gateway или события — `hotelflow-contracts-events`, расположенные рядом в `.agents/skills`.

## Проверка результата

- Проверки доменных переходов выполняются без БД, сети и generated-кода. Неудачный переход не оставляет частично изменённую сущность.
- Тест use case проверяет значимый порядок и последствия действий, включая отказ зависимости, а не просто повторяет getters/setters.
- Handler не решает, разрешена ли отмена/бронь/смена статуса. Storage не рассчитывает бизнес-решение; service не меняет статус вместо сущности.
- Общие DTO не содержат методов, принимающих доменные решения; domain не импортирует DTO ради удобства транспорта.
- Методы DTO и именованных типов коллекций разрешены для преобразования и обработки данных. Предпочитай их множеству повторяющихся helper-функций, сохраняя доменные инварианты в entity.
- Outbox и входящая идемпотентность уже включены. Inbox уже используется в Booking/Check-in; Notification намеренно работает без него. Автоматические RPC retry не добавляй без задачи.

## Структура и читаемость

- `types.go` сущности содержит статусы/перечисления, `version.go` — версию, `option.go` — опции восстановления.
- `types.go` конкретного use case содержит его входной DTO. Не выноси локальный input в общий `internal/dto`.
- DTO и entity не содержат `json`-тегов. HTTP/event payload сериализуется в своих адаптерах, через отдельные модели.
- Валидация группируется по конкретным инвариантам. Ранние возвраты с понятными ошибками предпочтительнее большой цепочки `||` или свалки строковых enum в одном методе. Не раздувай решение мелкими универсальными helper-функциями: используй методы соответствующих типов.
- Use case читается как последовательность действий сценария. Границы транзакций и единственный внешний вызов видны; выделенные методы называются по действию, а не скрывают всю работу за универсальным pipeline.
- Не зашивай seed UUID/таблицы соответствий в domain. Seed принадлежит данным стенда.

## Транспорт и сценарии Check-in

Каждый RPC — отдельный файл; структура и конструктор в service.go. Владелец сервиса внедряет конкретный `*usecase.Registry`, без интерфейсов на уровне gRPC. Разбор UUID и mapping ответа локальны методу; не создавай отдельные helpers/конвертеры. Образец — `ad-service/internal/app/ad/v1`. Gateway сохраняет прямые generated-клиенты.

Один use case на RPC и один на сценарий события. Kafka-хендлер вызывает use case, а не прикладной сервис. Input локален `types.go`, optional — `mo.Option[T]`. Узкие сервисы нужны только для осмысленной декомпозиции; не заводи пустой service registry.

Check-in владеет `CheckIn`, связанным с бронью через `booking_id`. Нет локальных сущностей Booking/Operation, source version брони и пакетов `application/.../booking`. Состояния и CAS принадлежат CheckIn; повторные и устаревшие reply обрабатываются доменными методами. HTTP-ключи и correlation-id событий — техническая идемпотентность, не самостоятельные доменные операции. Актуальные переходы и протокол — в `docs/check-in.md` и AGENTS.md.

## Получение времени

Время в use case получай напрямую через `time.Now()`; сущностям передавай готовое `time.Time`. Не добавляй `now func() time.Time`, Clock-интерфейсы, поля часов и параметры часов в конструкторы/registry. Не заменяй их глобальной изменяемой функцией ради тестов. Доменные границы времени тестируй через явный `time.Time`; сценарии проверяй без зависимости от точного момента запуска.

## Обогащение Hotel рейтингом

Общий DTO `internal/dto/hotel/rating.go` содержит только Rating, без импорта сущности. Hotel принимает его в `SetRating` и возвращает через `Rating`; такое использование простого DTO разрешено. Не вводи DTO-обёртку над Hotel с дополнительным рейтингом. GetHotel запрашивает рейтинг по UUID, устанавливает его и возвращает ту же сущность; не оборачивай одиночный объект в список ради доступа по `[0]`. Batch-обогащение списка устанавливает рейтинги тем же методом. Рейтинг в Hotels — данные текущего чтения из Review, не колонка каталога, не новый источник истины и не событие.
