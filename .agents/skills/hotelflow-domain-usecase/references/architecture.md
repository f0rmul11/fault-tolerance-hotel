# Слои и типы

Все пути ниже отсчитываются от корня отдельного Go-сервиса, например `services/booking`. Следуй этим путям даже там, где внешний пример использует `domain/value_object`, `application/dto` или `infrastructure/dal`.

| Путь | Ответственность |
| --- | --- |
| `internal/domain/entity` | Сущности, агрегаты, доменные коллекции сущностей, их переходы и инварианты |
| `internal/domain/vo` | Объекты-значения с доменным смыслом, валидацией и семантикой сравнения |
| `internal/application/usecase/<область>/<сценарий>` | Оркестрация одного бизнес-сценария, в том числе обработки конкретного события |
| `internal/application/service/<область>/<задача>` | Узкая задача получения, обогащения или подготовки данных для сценариев |
| `internal/dto/<область>/<dto>.go` | Данные без идентичности и жизненного цикла, передаваемые между несколькими слоями |
| `internal/infrastructure/storage/<сущность>` | Доступ к собственной БД, SQL, DAO и отображение в domain |
| `internal/infrastructure/gateway/<сервис>` | Исходящий адаптер к другому сервису |
| `internal/events/<событие>` | Определение и преобразование исходящего интеграционного события |
| `internal/pkg/<назначение>` | Технические вспомогательные пакеты без бизнес-правил |
| `internal/app/...` | Тонкие входные адаптеры существующего каркаса |
| `api/<сервис>/<область>/v1` | Исходные protobuf-контракты сервиса |
| `tools/migrations`, `tools/xo_templates` | SQL-миграции и шаблоны генерации xo |

Создавай только каталоги, необходимые текущей реализации; пустые слои и универсальные базовые классы не нужны.

Соблюдай [правила оформления Go](../../hotelflow-errors-tests/references/testing-go.md) во всех слоях: непустые тела методов, getters, Option и анонимных функций — многострочные, с табами Go и пустыми строками между логическими шагами. Не склеивай операторы через `;`; registry, конструкторы и составные литералы с несколькими полями раскрывай по строкам. Одного запуска gofmt/goimports для сжатого исходника недостаточно. Это правило действует также в `internal/pkg`, тестах и `hotelctl`, но не разрешает ручные правки generated-кода.

## Исключение: API Gateway

API Gateway — транспортный прокси по образцу исходного стенда. В нём нет слоёв application/usecase, application/service, domain, бизнес-DTO или infrastructure/gateway. Тонкие реализации в `internal/app` получают generated downstream-клиент напрямую из `initControllers`. Сценарии бронирования принадлежат Booking. Подробное оформление, Clay, auth и Buf — в [правилах API Gateway](../../hotelflow-contracts-events/references/api-gateway.md).

## Сущность, VO и DTO

Статусы и другие перечисления сущности размещай в `types.go`, код версии — в `version.go`. Сущность имеет доменную идентичность и жизненный цикл. Поля, определяющие состояние и инварианты, закрыты. Изменения выполняются методами предметной области, например `Confirm`, `Cancel`, `Occupy`, с проверкой допустимости перехода. Не добавляй публичный `SetStatus`, позволяющий обойти правило.

VO не имеет собственной идентичности, но выражает понятие домена: диапазон проживания, тип номера и т. п. Валидация и операции значения живут в VO, а правила, связывающие его с состоянием сущности, — в сущности. Не превращай VO в DTO только из-за отсутствия ID.

DTO нужен для передачи данных между слоями. Его место — `internal/dto/<область>/<dto>.go`. Входной DTO конкретного use case обязательно находится в его пакете, в `types.go`; локальный result также остаётся рядом, если не нужен нескольким слоям. Наличие поля `booking_id` само по себе не превращает DTO в сущность: это может быть лишь ссылка на чужую идентичность. Generated protobuf, DAO и интеграционное событие сохраняют свои специальные роли и каталоги.

DTO и сущности не имеют `json`-тегов. Для HTTP и событий создавай отдельные модели на соответствующей границе; не используй общий DTO как JSON schema.

**DTO могут иметь методы.** Для связной работы с моделями, структурами и коллекциями вводи именованные типы через `type` и методы на них вместо множества однотипных helper-функций. Например, `type Bookings []Booking` может иметь `IDs()` или группировку по полю, а DTO — метод преобразования, копирования или проверки собственного представления. Методы не превращают DTO в сущность. Инварианты, переходы состояния и определение доменного конфликта остаются у сущности/доменных коллекций. Не добавляй DTO обращения к БД/сети и не создавай обратные зависимости слоёв.

Для собственных методов нужен определённый в текущем пакете тип, например `type Bookings []Booking`; alias чужого типа через `type X = otherpkg.Y` не позволяет произвольно добавить ему методы. Тип должен выражать понятную задачу, а не создаваться формально для каждой функции.

Создание новой сущности и восстановление сохранённой различаются. Фабрика создания проверяет обязательные данные и устанавливает начальное состояние. При чтении БД DAO **обязательно** использует конструктор `With(id, opts ...Option)` и опции из `option.go`, как в order-service. Восстановление не генерирует ID, время, события и новые версии. Use case не использует эти опции для обхода бизнес-перехода.

```go
type Option func(*Booking)

func With(id uuid.UUID, opts ...Option) *Booking {
	booking := &Booking{id: id}

	for _, opt := range opts {
		opt(booking)
	}

	return booking
}
```

Опции `WithStatus`, `WithCreatedAt`, `WithVersion` и остальные восстанавливают все сохранённые поля. `WithVersion` устанавливает Old и сбрасывает pending new. Сам `With` не возвращает error. DAO просто преобразует поля и вызывает `With/Option`; отдельный `validateColumns` с проверками каждого SQL-поля не нужен. Инварианты проверяются доменными операциями; отдельную полную проверку при каждом чтении не вводи. Не восстанавливай запись через `NewBooking`, публичные setters или последовательность Confirm/Cancel.

Если в сервисе несколько типов сущностей, каждому нужен собственный пакет под `domain/entity`, например `domain/entity/booking` и `domain/entity/room`: тогда возможны `bookingentity.With` и `roomentity.With` со своими `Option`. В одном Go-пакете нельзя объявить несколько разных `With`/`Option`. Для единственной сущности допустим пакет непосредственно `domain/entity`.

Сущность не обращается к storage, gateway или конфигурации процесса. Внешние данные и время передаются ей явно. Не возвращай наружу изменяемую ссылку или slice, через который можно обойти её инварианты.

## Где проверять конфликтующие брони

Storage получает релевантные записи-кандидаты по техническим фильтрам: владелец, объект, период. Use case передаёт данные сущности/агрегату или доменной коллекции из `domain/entity`. Именно доменный метод определяет пересечение периодов, блокирующие состояния и допустимость операции.

SQL может ограничивать объём выборки, но набор кандидатов должен включать все записи, нужные доменному правилу. Проверку нельзя оставлять только в SQL или дублировать набором `if` в use case. Для интервальной брони границы берутся из спецификации: `[starts_at, ends_at)`. Бронь, заканчивающаяся в момент начала следующей, сама по себе не конфликтует.

Hotels владеет отдельными сущностями Hotel и Room, описанием отелей/номеров, официальными звёздами, координатами, удобствами и min/max длительности. Review владеет только пользовательскими рейтингами отелей; у номеров рейтинга нет. ListHotels/GetHotel обогащаются одним batch RPC в Review, который читает весь набор одним SQL. GetRoom/ListRooms не зависят от Review. Booking владеет гостем, номером, периодом и статусом брони, получает условия из Hotels до транзакции и проверяет занятость в своей БД. Отдельных сервисов Room, Search и Availability нет.

Period — VO [starts_at, ends_at), произвольное начало, UTC, точность до микросекунд. Одна бронь содержит один непрерывный период. Seed Hotels задаёт минимум 12 часов; максимум зависит от номера. Создание одной локальной транзакцией сохраняет CONFIRMED, ключ идемпотентности и outbox. Порядок в транзакции: проверка длительности, insert брони, outbox, commit. Ключ проверяется до вызова Hotels: сохранённый повтор возвращает бронь. При гонке вставок один запрос получает конфликт; advisory lock и повторное чтение ключа в confirm не нужны. Пересечения запрещает EXCLUDE USING gist по room_id и tstzrange; room lock и предварительное чтение пересечений не нужны. Подробности — `docs/booking.md`.

## Use case и внутренний service

Use case отвечает за порядок чтений, вызовов домена, сохранений и интеграций. Бизнес-решение остаётся внутри сущности. Use case обрабатывает её результат, но не устанавливает состояние вместо неё. Один HTTP/gRPC handler или обработчик события делегирует соответствующему use case; несколько транспортов одного сценария не порождают разные реализации бизнес-логики.

`internal/application/service` выполняет одну конкретную задачу, например собирает данные из gateway и storage для обогащения ответа. Он может быть нужен одному или нескольким use case; переиспользование не является обязательным условием выделения. Название выражает задачу: например, `internal/application/service/booking/finalize`, пакет `finalize`, вместо слитного `bookingfinalization`. Если use case разрастается, выноси завершённую задачу в такой сервис: например, завершение бронирования с перечитыванием сущности и атомарным сохранением результата вместе с outbox. Use case остаётся коротким оркестратором, доменные переходы остаются методами сущности. Не создавай универсальный `BookingService`, содержащий все сценарии, или service ради простой переадресации вызова.

Обогащение ответа не должно незаметно менять сохраняемое состояние, статус и версию сущности. При возможности представляй результат обогащения DTO.

## Зависимости и wiring

- Domain зависит от собственных entity/vo и необходимых библиотек значений; допускается нейтральный сервисный пакет ошибок по форме ordererror; не импортирует application, dto, events-конвертеры, infrastructure, protobuf, xo, SQL/pgx, Kafka и транспортные фреймворки.
- Use case зависит от domain, DTO, узких service/портов и предусмотренной абстракции transaction. Он может вызвать конвертер исходящего события после доменного перехода.
- Логика Service зависит от domain/DTO и узких портов. Она не импортирует use case или concrete storage/gateway. Исключение для wiring-файла registry описано ниже.
- Infrastructure реализует эти порты, переводит данные и ошибки во внутренние типы. Concrete реализации собираются через конструкторы registry слоёв под управлением `internal/init.go`.
- Generated-модели остаются на границе соответствующего адаптера. Go-пакеты разных сервисов не импортируют чужой `internal`; взаимодействуют по контрактам.

## Ручной DI и registry

Используй подход order-service: `App` хранит собранные компоненты, `internal/init.go` создаёт их в порядке зависимостей, `registry.go` соответствующего слоя создаёт его компоненты. DI-framework, reflection container и глобальный service locator не нужны.

- `internal/infrastructure/storage/registry.go` получает pool и создаёт storage.
- `internal/infrastructure/gateway/registry.go` принимает `map[string]grpc.ClientConnInterface`, выбирает соединения по константам имён сервисов из `config` и создаёт клиентов/gateway. `initGateway` передаёт всю map; клиент собирается как `NewClient(NewExternalClient(conn[config.ServiceName]))`. Gateway передаёт входящий context без собственного timeout.
- `internal/application/service/registry.go` собирает нужные узкие сервисы, если они есть.
- `internal/application/usecase/registry.go` собирает use case. Не возвращай сценарии в `application/service` только из-за пути примера.
- `internal/init.go` связывает registry и транспортные адаптеры, регистрирует ErrorInterceptor и lifecycle ресурсов.

**Registry является частью composition root.** Его constructor может принимать конкретные registry, pool-обёртки и компоненты других слоёв и импортировать их реализации. Передавай отдельному use case/service только нужные поля как узкие интерфейсы. Не передавай ему весь registry или raw pool, не получай зависимости из глобального контейнера во время запроса. Транспортный adapter может получить registry use case по образцу и делегировать нужному полю.

Registry содержит typed fields и wiring, без SQL, RPC, бизнес-ветвлений и скрытых побочных эффектов constructor. Инициализация соединений, ошибки старта и закрытие ресурсов остаются в init/lifecycle. Leaf-пакеты не импортируют свой родительский registry обратно: не создавай циклы. Часы учебного стенда остаются явной зависимостью. UUID брони создавай через uuid.NewV4() непосредственно в use case; не добавляй ID generator/newID в DI только ради тестов. Сохраняй существующий порядок graceful shutdown; не копируй устаревшую повторную остановку Clay из образца.

## Вспомогательные пакеты

Используй `internal/pkg/<назначение>` отдельного сервиса, как в образце. Туда относятся transaction, connector, closer, healthcheck, технические ошибки, а также каталоги generated-кода `pb`, `pb/external`, `xo`.

Пакет не должен знать предметные понятия Booking/Room, сценарии, доменные переходы или конкретные infrastructure-адаптеры. Не создавай свалку `utils`, общий DTO для всех областей или пакет `pkg`, который импортирует application обратно. Outbox здесь — технический механизм хранения/доставки; определения бизнес-событий остаются в `internal/events`.

Уже выбранные outbox/event/pipe/worker/connectors бери из указанного order-service, не переписывай их упрощёнными аналогами. Не копируй из примера посторонние helpers и зависимости. Переноси только нужный пакет вместе с проверенными зависимостями, адаптируя module paths и регистрацию ресурсов в lifecycle сервиса.

## Конкретный порядок инициализации

Следуй `order-service/internal/{app.go,init.go}`: `App` хранит компоненты, init-цепочка вызывает отдельные `initPostgres`, `initStorage`, `initGateway`, `initMessageBus`, `initOutbox`, `initServices`, `initUsecases`, `initControllers` по зависимостям. Ненужные слои не создаются. `postgres.Pool(ctx, dsn)` живёт в скопированном connector; сборка всех слоёв в `business.go`/`initBusiness` запрещена.

Регистрация контроллеров без ветвлений по nil. Обязательная зависимость должна существовать; ошибка инициализации прерывает старт. Не добавляй `New(nil, nil)` и ответ «бизнес-режим выключен» как резервный путь.

Тип `Role` и константы ролей объявляются в `internal/domain/entity/types.go`, а DTO контекста ссылается на этот доменный тип.

Роли/структура request context проверяются единожды на транспортном входе, по policy конкретного метода. Use case получает проверенную идентичность; сравнение guest_id владельца брони с caller остаётся в сценарии чтения. Другой вход (например consumer) обязан выполнить свою граничную проверку, а не рассчитывать на HTTP middleware.

## Транспорт и сценарии Check-in

Каждый RPC — отдельный файл; структура и конструктор в service.go. Владелец сервиса внедряет конкретный `*usecase.Registry`, без интерфейсов на уровне gRPC. Разбор UUID и mapping ответа локальны методу; не создавай отдельные helpers/конвертеры. Образец — `ad-service/internal/app/ad/v1`. Gateway сохраняет прямые generated-клиенты.

Один use case на RPC и один на сценарий события. Kafka-хендлер вызывает use case, а не прикладной сервис. Input локален `types.go`, optional — `mo.Option[T]`. Узкие сервисы нужны только для осмысленной декомпозиции; не заводи пустой service registry.

Check-in владеет `CheckIn`, связанным с бронью через `booking_id`. Нет локальных сущностей Booking/Operation, source version брони и пакетов `application/.../booking`. Состояния и CAS принадлежат CheckIn; повторные и устаревшие reply обрабатываются доменными методами. HTTP-ключи и correlation-id событий — техническая идемпотентность, не самостоятельные доменные операции. Актуальные переходы и протокол — в `docs/check-in.md` и AGENTS.md.

## Часы

Время в use case получай напрямую через `time.Now()`; сущностям передавай готовое `time.Time`. Не добавляй `now func() time.Time`, Clock-интерфейсы, поля часов и параметры часов в конструкторы/registry. Не заменяй их глобальной изменяемой функцией ради тестов. Доменные границы времени тестируй через явный `time.Time`; сценарии проверяй без зависимости от точного момента запуска.
