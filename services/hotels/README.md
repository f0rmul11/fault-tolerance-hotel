# Hotels

Каталог отелей и номеров. Own PostgreSQL `hotels`, отдельные сущности Hotel и Room. Четыре gRPC-метода: ListHotels, GetHotel, ListRooms, GetRoom. Публичный HTTP предоставляет Clay в API Gateway.

GetHotel читает полный снимок Hotel с рейтингом через отдельный метод `infrastructure/adapter/hotel.GetWithSoftTTL`. ListHotels сохраняет один batch-запрос Review без кеширования списка; комнаты и min/max бронирования читаются без Review. Рейтинг не сохраняется в БД Hotels.

Hotels подписан на `review.rating.events.v1`, consumer group — `hotels-review-events`, общая для всех реплик. Структура consumer перенесена из Check-in: messagebus registry → subscriber → handler топика → event router → handler rating_changed → use case refresh → адаптер. Inbox отсутствует. Обработчик ставит tombstone через CAS, читает Hotel из storage и актуальный рейтинг из Review и сохраняет полный снимок через CAS с полученным токеном. Offset подтверждается только после успешного обновления. Ошибка источника, degraded-рейтинг или конфликт CAS возвращаются consumer'у без подтверждения сообщения. Повторные и запоздалые события перечитывают источники; значения рейтинга из события не используются.

Для предыдущих этапов урока в read.go сохранены исходный `Get` с обычным SET и закомментированный `GetWithCAS`. Активный use case вызывает `GetWithSoftTTL`. Старый `Get` предназначен для отдельной демонстрации: его нельзя одновременно использовать с защищённым заполнением кеша.

## Soft TTL и недоступность Review

В payload хранятся абсолютные `soft_deadline` и `hard_deadline`. Их отсчитываем от начала успешной загрузки источников. Формат ключа — `v2:hotel:<uuid>`; версия формата не является CAS-токеном.

| Состояние | Что получает клиент | Обновление кеша |
| --- | --- | --- |
| До soft deadline | Сохранённую карточку | Не требуется |
| От soft до hard deadline | Допустимую старую карточку немедленно | Фоновая загрузка и CAS с исходным токеном |
| После hard deadline / промах | Свежую карточку из источников | CAS после успешной загрузки |
| Review недоступен после hard deadline | Отель с `Rating.Degraded=true`, без старого рейтинга | Неполную карточку не кешируем |
| Tombstone | Читаем источники; при недоступности Review — явная деградация | Обычный читатель не заменяет tombstone |

Для GetHotel без требования минимальной версии деградация на Unavailable/DeadlineExceeded применяется в адаптере независимо от флага fallback предыдущего урока. Прочие ошибки Review возвращаются вызывающему коду. Ошибка storage не позволяет собрать карточку и также возвращается клиенту. Отмена исходного запроса не превращается в успешный fallback. Политика ListHotels остаётся прежней.

Настройки `config/config.yaml`: soft TTL — **20 секунд**, hard TTL — **1 минута**, timeout загрузки — **3 секунды**.

Каждое чтение stale-карточки запускает отдельное фоновое обновление. Оно не зависит от отмены пользовательского запроса и ограничено `refresh_timeout`. В этом уроке нет объединения запросов, лимита фоновых задач и задержки повторов. Защиту от одновременных загрузок одного ключа через singleflight добавим в следующем уроке. Конкурентную публикацию снимков уже защищает CAS.

Только успешная загрузка полного снимка назначает новые deadlines. Ошибка refresh не меняет ни payload, ни срок хранения. Физический TTL Valkey чуть длиннее hard deadline — на `refresh_timeout`, чтобы не терять токен во время ограниченного по времени чтения. Это не разрешает отдавать старый рейтинг после hard deadline. Если ключ с ненулевым ожидаемым токеном исчез, CAS возвращает конфликт, а не воссоздаёт его. Событийный Refresh устанавливает tombstone до чтения источников, поэтому уже запущенное фоновое обновление со старым токеном не сможет перезаписать новый снимок.

Границы гарантии: время на репликах должно быть синхронизировано; hard deadline ограничивает возраст снимка в кеше, а не отставание самих источников. CAS не устраняет задержку доставки события, не делает чтение двух источников атомарным и не отзывает уже прочитанный ответ. Счётчик версий не даёт гарантии от ABA при потере и повторном создании ключа, откате состояния после failover или переполнении. Для этих отказов нужны более сильные токены/версия источника; текущая демонстрация рассчитана на сохранность ключей до завершения ограниченных по времени чтений (в стенде используется `noeviction`).

Подход опирается на [AWS Builders’ Library](https://aws.amazon.com/builders-library/caching-challenges-and-strategies/) — soft/hard TTL, [Cloudflare](https://developers.cloudflare.com/cache/concepts/revalidation/) — stale-while-revalidate в ограниченном окне, и [Scaling Memcache at Facebook](https://www.usenix.org/system/files/conference/nsdi13/nsdi13-final170_update.pdf) — токены для защиты от stale sets. Это адаптация принципов к нашему CAS, а не реализация распределённых leases из статьи Facebook.

### Минимальная версия рейтинга со стороны клиента

Review уже возвращает `rating_version` в ответах AddHotelRating и GetHotelRatings. Hotels сохраняет её в DTO, payload кеша и ответах GetHotel/ListHotels. Это версия агрегата рейтинга конкретного отеля, независимая от `Entry.Version`, который защищает запись в Valkey.

GetHotel принимает `min_rating_version`. В HTTP это `GET /v1/hotels/{hotel_id}?min_rating_version=42`, в gRPC — поле `GetHotelRequest.min_rating_version`. Значение 0 (в том числе отсутствие параметра) сохраняет обычное поведение soft/hard TTL. Отрицательное значение возвращает InvalidArgument (HTTP 422).

Снимок разрешён, если его `rating_version >= min_rating_version` и hard deadline не истёк. Более старый снимок обходим синхронным чтением Storage и Review, даже если soft TTL ещё не истёк. После чтения проверяем версию до возврата и публикации через CAS. Если Review недоступен, вернул degraded или версию ниже требуемой, возвращаем Unavailable (HTTP 503), не выдаём старый рейтинг и не меняем кеш. Остальные ошибки источников сохраняются. Tombstone по-прежнему заполняет только обработчик инвалидации; проигрыш CAS не мешает вернуть уже прочитанный ответ, удовлетворяющий требованию клиента.

Клиент хранит максимум увиденной версии отдельно для каждого `hotel_id` и передаёт её при последующих чтениях. После успешной записи в Review это даёт read-your-writes для рейтинга; это не требование получить ровно указанную версию и не гарантия атомарного снимка Hotels + Review. При недоступности требуемой версии адаптер не делает циклических повторов. В HTTP JSON protobuf `int64` сериализуется строкой: `"rating_version": "42"`.

Демонстрация: прогреть карточку, приостановить consumer Hotels, выполнить AddHotelRating через gRPC Review и запомнить версию из ответа. Обычное чтение до soft TTL может вернуть старую карточку; запрос с `min_rating_version` обойдёт её и прочитает актуальный рейтинг. После демонстрации возобновить consumer. Отдельного HTTP-метода записи в Review у шлюза нет.

Проверка с отдельным тестовым Valkey (из services/hotels):

```sh
HOTELS_TEST_VALKEY_ADDRESS=127.0.0.1:6379 GOWORK=off go test -race -tags integration ./internal/infrastructure/adapter/hotel/...
```

### Проверка и демонстрация

1. Получить карточку через GetHotel: в Valkey появится полный снимок с двумя deadlines.
2. Через 20 секунд повторить запрос: ответ использует старый снимок; фоновое обновление меняет его версию и deadlines.
3. Остановить Review после успешного прогрева. До hard deadline карточка доступна; неудачные refresh не сдвигают deadlines.
4. После hard deadline запрос возвращает отель с признаком недоступного рейтинга. Затем восстановить Review: следующий запрос загрузит свежую карточку.

`kafka_brokers: ["localhost:9092"]` переопределяется через `hotelctl` на `KAFKA_BROKERS=kafka:9092`, как в Check-in. Группа включена в общий reset Kafka. Собственный топик создаёт Review; Hotels его только читает.

`make generate` выполняет Buf lint/build и генерацию собственных контрактов и внешнего клиента Review. `make test` запускает race-тесты. Миграции/seed: tools/migrations и tools/seed.

Hotels разворачивается в **3 реплики**, RollingUpdate: `maxUnavailable: 0`, `maxSurge: 1`.
Readiness допускает Pod после первой успешной загрузки конфигурации из прикладного etcd.
При последующей потере etcd сохраняется последнее валидное состояние; startup и liveness
не зависят от синхронизации. Полученный из etcd false не делает Pod неготовым.

`ListRooms` проверяет `rooms_list_enabled` через внедрённый `*config.Client` перед чтением БД.
При false возвращается gRPC FailedPrecondition / HTTP 409 «Получение списка номеров отключено».
Default — false. Остальные RPC этим флагом не управляются; обращений в Review у ListRooms нет.

Из корня проекта:

```sh
./bin/hotelctl config set hotels rooms_list_enabled true
./bin/hotelctl config get hotels rooms_list_enabled
```

Успешный set подтверждает запись в etcd; каждый Pod применяет обновление в фоне.
Старый ключ hotels_list_enabled больше не используется. Значения из etcd автоматически не переименовываются.
