# Проверка идентификаторов — 14 октября 2026

Изолированное окружение: PostgreSQL 16, Kafka 3.9.1, свежие схемы Hotels/Review/Booking/Check-in. Запущены пять сервисов с актуальными Buf-контрактами. Существующий k3s и его сообщения не изменялись.

Проверено через HTTP и реальные БД/брокер:

- Отели используют UUID v4; номера — короткие числовые ID в строках. Номера с ID 1 и 11 имеют одинаковый number="101" в разных отелях и разные значения room_type.
- Создание и чтение брони возвращают room_id="1", room_number="101", room_type="Standard".
- Outbox → Kafka → inbox доставляет UUID aggregate_id/correlation_id и новый снимок номера; ключ Kafka совпадает с UUID брони. Check-in сохраняет снимок и возвращает его через HTTP.
- Изменение каталога после создания не меняет снимок сохранённой брони: повтор с тем же ключом возвращает исходный ответ без второго события.
- Шесть параллельных попыток занять один номер: один HTTP 200 и пять HTTP 409. Совпадение номера двери в разных отелях не создаёт ложного конфликта.
- CheckAvailability возвращает строки числовых ID и исключает занятые номера.
- Активация и отмена проходят request/reply через Kafka; отменённый номер можно забронировать снова.
- Некорректные/неположительные ID номера отклоняются с HTTP 422.

Проверки кода:

- `go test -race` для Booking, Check-in, Hotels, Review, API Gateway и Notification; также существующие lifecycle-тесты.
- `go vet` для этих шести модулей.
- Генерация через закреплённые Docker Buf targets; API Gateway — существующий `generate-offline` с внешним кешем импортов.
- Goose-миграции и xo-генерация из свежих изолированных БД; GiST EXCLUDE сохранён.

Фактическое событие и результаты: [identifiers-verification.json](identifiers-verification.json). Старые отчёты описывают прежние модели; это исторические результаты, они не переписаны под новую схему.
