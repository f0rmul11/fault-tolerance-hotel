# Проверка атомарного бронирования — 12 октября 2026

Историческая проверка версии со слотами. Актуальная модель с Period и EXCLUDE проверена в [period-booking-verification.md](period-booking-verification.md).

Проверена новая схема: Booking владеет бронью и занятостью, Room — каталогом; Availability удалён. Тесты выполнялись на отдельных PostgreSQL 16 / Kafka 3.9.1 и собранных локальных процессах Room, Booking, Clay Gateway. Работающий k3s-стенд и его данные не пересоздавались.

## Код и генерация

- Buf format/lint/build и генерация Booking, внешнего Room-клиента, публичного Clay API и внешнего Booking-клиента завершились успешно. Для Gateway использован существующий `generate-offline.sh` с внешним кешем protobuf imports, без third_party.
- Goose применил исходные миграции на чистую БД; xo сгенерирован из новой схемы с `idempotency_key` и UNIQUE по гостю/ключу.
- `go test -race`, `go vet`, `go build` прошли для всех шести сервисов и hotelctl. Lifecycle-тесты запускались с разрешением локальных TCP-портов. Проверены актуальные deployment manifests и последовательность миграций двух владельцев.
- Новые unit-тесты проверяют сравнение состава при повторе, нормализацию слотов, доменные пересечения, быстрый повтор без Room, отказ зависимостей, фильтрацию доступных номеров и transport mapping ключа.

## PostgreSQL

`BOOKING_TEST_POSTGRES_DSN=... go test -race -v ./services/booking/internal/application/service/booking/confirm` — 10 сценариев пройдены:

1. 24 конкурентных пересекающихся запроса: одна бронь, один слот, одно событие.
2. 24 параллельных повтора ключа: одна бронь с двумя слотами, один event; ID, исходный request_id и версия совпадают.
3. Один ключ одновременно для разных номеров: один успех, один Conflict.
4. Ключ изолирован по гостю; изменение состава под уже сохранённым ключом запрещено.
5. Конфликт одного слота откатывает весь набор; разрыв и соседняя граница остаются свободными.
6. Ошибка после записи outbox: бронь, слоты и событие откатываются, ключ можно повторить.
7. Отмена контекста после записи: полный rollback, последующий повтор успешен.
8. Реальное завершение текущего PostgreSQL backend: полный rollback, повтор успешен.
9. Повтор после намеренно неиспользованного успешного ответа возвращает исходную запись. Это проверка восстановления по ключу, а не инъекция сетевого сбоя непосредственно в COMMIT.
10. Слоты короче min или длиннее max не оставляют записей.

## HTTP и Kafka

Через настоящий Clay HTTP → Booking gRPC → Room gRPC:

- Создание возвращает 200 / CONFIRMED v1; чтение и повтор с новым request_id возвращают исходную бронь.
- Изменённый состав под тем же ключом и пересечение под новым ключом дают 409; пустой ключ — 422.
- Проверка доступности исключает занятый номер, возвращая остальные девять seed-номеров.
- После остановки Room повтор сохранённой операции успешен; новый запрос даёт 503 без частичной записи.
- После остановки Kafka новая бронь сохраняется, событие остаётся pending. Повтор не добавляет вторую запись outbox.
- После запуска Kafka оба события доставлены; pending = 0. Независимым consumer прочитаны две записи `booking.confirmed.v1`, их aggregate_id совпадают с двумя бронями, event_id различны.

[Фактические ID и записи Kafka](atomic-booking-verification.json).

Relay сохраняет at-least-once, без обещания exactly-once. Эти проверки не доказывают отказоустойчивость PostgreSQL при потере диска, production-аутентификацию или согласованность ещё не реализованных изменений каталога. Существующая БД старой модели требует явного пересоздания перед запуском новой версии; обычные генерация и деплой не удаляют данные.
