# Границы сетевых сбоев HotelFlow

Актуально для шести сервисов и четырёх отдельных PostgreSQL. Требования и гарантии —
в [спецификации](specification.md); этот документ описывает последствия уже существующих
вызовов и записей, а не добавляет новые паттерны или упражнения.

## Создание брони

| Граница сбоя | Результат и восстановление |
| --- | --- |
| Клиент → Gateway → Booking до обработки | Записи нет; повтор с тем же idempotency_key |
| Booking → Hotels.GetRoom | Чтение до транзакции: ошибка не оставляет бронь. Сохранённый повтор читается из Booking и не требует Hotels |
| INSERT брони / outbox до commit | Одна локальная транзакция; ошибка откатывает оба изменения |
| Ответ на commit или HTTP-ответ потерян | Клиент не знает результат; повтор того же ключа и состава читает сохранённую бронь либо создаёт её, если commit не состоялся |
| Два новых запроса с одним ключом | unique (guest_id, idempotency_key) не допускает двух записей. Проигравшая вставка получает Conflict; отдельного advisory lock нет |
| Две пересекающиеся брони номера | EXCLUDE не допускает обе записи. 23P01 нужного ограничения → NewBusinessErr/HTTP 409; deadlock 40P01 → Conflict/HTTP 409 |
| Проверка доступности → создание | Прочитанный список может устареть; окончательное решение принимает EXCLUDE при INSERT |
| Условия Hotels изменились после чтения | Используется полученный снимок. Каталог сейчас read-only; редактирование потребует отдельного решения о версиях условий |

Нет распределённой транзакции, сохранённого PENDING и отдельного резервирования в Availability.
Бронь либо CONFIRMED вместе с outbox, либо не сохранена. Таймаут сам по себе не доказывает rollback.

## События и заселение

| Граница сбоя | Результат и восстановление |
| --- | --- |
| PostgreSQL → outbox relay → Kafka | При недоступной Kafka запись остаётся в outbox; relay повторяет отправку после восстановления |
| Kafka приняла событие, ACK или отметка processed_at потеряна | Возможен дубль с тем же correlation_id; доставка at-least-once |
| Consumer сохранил inbox, offset commit потерян | Повтор поглощается unique (correlation_id, topic) в inbox |
| HTTP активации/отмены Check-in | Ключ (actor_id, key), состояние CheckIn и outbox сохраняются одной транзакцией. Повтор возвращает текущее состояние того же CheckIn |
| Kafka недоступна после принятия действия | CheckIn остаётся ARRIVING/CANCELING до ответа; сохранённая команда ожидает в outbox. Локального таймера отмены нет |
| Booking применяет команду Check-in | processed_events, CAS-переход Booking и reply outbox сохраняются одной транзакцией. Техническая ошибка откатывает их вместе |
| Business commit Booking успешен, inbox processed_at не сохранён | Повтор команды распознаётся по processed_events.correlation_id и не создаёт второй переход или reply |
| Бизнес-отказ Booking | booking.checkin-rejected.v1 возвращает CheckIn в предыдущее состояние с русским пояснением |
| Ответ повторился или пришёл поздно | Домен CheckIn проверяет ожидаемую версию действия; старый ответ не изменяет новое состояние |
| Notification записал лог, offset commit потерян | Лог может повториться: inbox и дедупликация намеренно отсутствуют |
| Consumer получил некорректное сообщение | Автоматического DLQ/пропуска нет; сообщение может задерживать обработку и требует разбора причины |

## Каталог и ограничения восстановления

Hotels → Review — один batch RPC для ListHotels/GetHotel. Сбой Review возвращает ошибку чтения
отелей с рейтингом; GetRoom/ListRooms и путь бронирования от Review не зависят.
Все эти вызовы читающие и не оставляют частичных записей.

Inbox/outbox не заменяют резервное копирование и не гарантируют восстановление после потери диска.
При утрате БД потребителя и сохранённых Kafka offsets требуется восстановить данные либо отдельно
организовать replay в пределах retention. Один локальный k3s, один брокер и PostgreSQL на сервис
не обеспечивают высокую доступность инфраструктуры.

`hotelctl reset --yes` очищает согласованный учебный набор БД, топиков и offsets при остановленных
приложениях. Это подготовка стенда к новому прогону, а не восстановление потерянных бизнес-данных.
