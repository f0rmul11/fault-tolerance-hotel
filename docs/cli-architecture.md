# Архитектура hotelctl

## Архитектурный образец

Структура команд повторяет подход **kubectl v1.35.2**:

- [Тонкая точка входа cmd/kubectl](https://github.com/kubernetes/kubernetes/blob/v1.35.2/cmd/kubectl/kubectl.go).
- [Конструктор команды, Options, Complete → Validate → Run](https://github.com/kubernetes/kubectl/blob/v0.35.2/pkg/cmd/create/create_namespace.go).
- [Фабрика зависимостей](https://github.com/kubernetes/kubectl/blob/v0.35.2/pkg/cmd/util/factory.go).

Это собственная реализация предметных команд HotelFlow по этой архитектуре.
Не копируются ненужные внутренние подсистемы kubectl — плагины, схемы всех его команд и глобальные exit-хелперы.
Ошибки поднимаются через `RunE` к единственной точке выхода в `main`.

## Слои

| Каталог внутри hotelctl | Ответственность |
|---|---|
| `cmd/hotelctl` | stdin/stdout, сигналы, запуск корневой команды, код выхода |
| `pkg/cmd` | дерево Cobra-команд и общие флаги |
| `pkg/cmd/<command>` | `NewCmd…`, `Options`, `Complete`, `Validate`, `Run` |
| `pkg/cmd/util` | интерфейс и реализация фабрики, общие параметры операций |
| `internal/config` | поиск и строгая проверка hotel.yaml, выбор сервисов |
| `internal/stand` | сценарии запуска, сборки, деплоя, остановки и диагностики |
| `internal/docker` | официальный Docker SDK: контейнер, сеть, том, образы, exec |
| `internal/kube` | client-go, Kustomize, server-side apply, ожидание rollout, логи |
| `internal/project` | атомарное состояние, права файлов, блокировка операций |
| `internal/diagnostics` | проверки API с компьютера |
| `internal/iostreams` | внедряемые потоки ввода/вывода |

Команды не создают Docker/Kubernetes-клиенты при построении справки и не используют глобальный mutable state.
`Complete` разрешает конфигурацию и аргументы; `Validate` проверяет параметры;
`Run` получает зависимости из фабрики и вызывает сценарий.
Сценарии не зависят от Cobra; CLI-тесты подменяют фабрику без Docker и Kubernetes.

## Один k3s

В Docker создаются один контейнер k3s, одна сеть и один постоянный том.
Это [официальный способ запуска образа k3s](https://docs.k3s.io/installation/configuration#configuration-with-container-image),
использующий Linux-среду Docker. Kubernetes API, HTTP, gRPC и admin публикуются через порты контейнера.
Traefik и ServiceLB отключены: для одного входного gateway используются прямые NodePort Service.
Admin Service публикует неготовые endpoints, рабочие Service учитывают readiness.

Docker-контекст читается через библиотеки Docker; поддерживаются локальные Unix socket и Windows named pipe.
Удалённые Docker-контексты отвергаются, потому что localhost пользователя не является хостом удалённого daemon.
Для k3s требуется privileged-контейнер; rootless Docker не поддерживается.

В hotelctl нет shell-скриптов, `sh -c` и вызовов локальных `docker`, `curl` или `kubectl`.
Образы собираются через Docker Engine Build API, передаются в контейнер через API и импортируются
встроенным `ctr`. Команда `kubectl` вызывает встроенный бинарник внутри контейнера через Docker Exec API.
Аргументы передаются массивом, без shell-интерполяции.

## Состояние и повторные операции

`.local/hotelctl/state.json` хранит owner ID, настройки runtime и теги собранных образов.
Перед созданием ресурсов сохраняется owner ID; повторный `up` продолжает работу после частичного сбоя.
При добавлении опубликованных портов `up` пересоздаёт контейнер с тем же томом и owner ID.
Каждый ресурс Docker имеет метки владельца. `destroy` сначала проверяет все метки и только затем удаляет ресурсы.
Файлы состояния и kubeconfig создаются с правами 0600, каталог — 0700; запись выполняется через временный файл и rename.
Мутации защищены файловой блокировкой. Исходные манифесты при деплое не переписываются.

## Добавление возможностей

Новый сервис: каталог в `services/`, Dockerfile, Kustomize-манифесты и имя в списке `hotel.yaml`.
Стандартные пути, имя образа и проверочный Echo-метод вычисляются по имени сервиса; объект вместо строки позволяет переопределить значения.
Текущий контракт сервиса предполагает один Deployment для ожидания готовности и выбора Pod для логов.
CLI ожидает Deployment приложений и инфраструктуры, а также Job миграций и reset. StatefulSet не является целевым workload.

Новая команда: отдельный пакет в `pkg/cmd`, конструктор `NewCmd…` и регистрация в `pkg/cmd/cmd.go`.
Новый сценарий: метод слоя `internal/stand`; сетевые и файловые детали остаются в адаптерах.

Для проверок используются тесты команд без Docker, тесты владения ресурсами через HTTP test server,
тесты Kustomize/готовности на fake Kubernetes client и настоящий локальный запуск k3s.

`reset --yes` сохраняет исходные реплики и этап в State.Reset, выполняет отдельный Job очистки БД/Kafka и восстанавливает приложения. Пока этап не завершён, up/deploy не запускают сервисы. Подробности — [спецификация](specification.md#запуск-проверка-и-сброс).
