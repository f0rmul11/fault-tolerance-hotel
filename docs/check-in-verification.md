# Проверка Booking ↔ Check-in — 13 октября 2026

Проверена модель с собственной сущностью CheckIn и явными booking_activated / booking_canceled. Старый changed-протокол и сущность Operation удалены.

## Автоматические проверки

- `go test` и `go test -race` для Booking, Check-in, Room и API Gateway: успешно, включая существующие lifecycle-тесты.
- `go vet` тех же четырёх сервисов: успешно.
- Табличные проверки переходов Booking/CheckIn, устаревших reply, диапазона Europe/Moscow и отказа событий без корректного correlation-id.
- Проверены тип, UUID и совпадение correlation-id в body/headers для всех шести видов событий; у reply собственный ID.
- Buf lint/build/generate для новых локальных контрактов Check-in и gateway; external-клиент шлюза генерируется из Check-in. xo создан из реально применённых миграций в отдельной БД.
- Пакет inbox: 10 Go-файлов каждого сервиса совпадают с эталоном payment-service по токенам, кроме module imports. Уникальность correlation-id/topic задана миграцией. Skills прошли quick_validate.

## Сквозная проверка

Изолированный PostgreSQL 16, Kafka 3.9.1 и локальные Room/Booking/Check-in/API Gateway. Данные и процессы рабочего k3s не изменялись.

1. Создание брони → booking.confirmed → ожидаемый CheckIn. Список фильтрует начало диапазона; московская полночь, вчерашний заезд и явный диапазон проверены.
2. Роли и identity оператора проверяются interceptor; GUEST не получает доступ к ручкам Check-in.
3. ARRIVING → Kafka → Booking ACTIVE v2 → CheckIn CHECKED_IN v3. Заселённый гость исчезает из списка ожидаемых.
4. Повтор HTTP-ключа не создаёт вторую команду; замена действия с тем же ключом даёт 409. Старый ключ активации после отмены возвращает CANCELED.
5. Повторная обработка inbox после business commit не меняет версии и не добавляет reply. Повтор создания не сбрасывает CheckIn.
6. Kafka остановлена: создание и отмена сохраняют outbox, конкурирующее действие отклоняется. После запуска брокера обе стороны сходятся, отмена освобождает номер для той же даты.
7. Отмена проверена из CONFIRMED и ACTIVE. Физическая повторная отправка outbox сохраняет correlation-id и не создаёт второй inbox.
8. Бизнес-отказ Booking возвращается отдельным событием, снимает ожидание CheckIn и содержит русское пояснение.
9. Недоступная таблица outbox Check-in откатывает состояние и HTTP-ключ. В Booking ошибка записи outbox откатывает статус и correlation-id receipt. Повтор после восстановления завершается успешно.
10. Конкурентные активация/отмена принимают ровно одно действие благодаря CAS. Обе пары inbox/outbox в конце пусты по pending.

В диагностическом SQL тестового скрипта исправлено имя `header` на `headers`; проверка заголовков и опустошения очередей повторена на тех же данных успешно. Это не изменение приложения.

Полный перечень результатов — [JSON](check-in-verification.json). Проверки подтверждают перечисленные сценарии, а не отсутствие любых возможных распределённых сбоев. Существующий стенд не пересоздавался; новая схема требует явного пересоздания учебных БД при развёртывании, совместимость не сохраняется по требованию пользователя.
