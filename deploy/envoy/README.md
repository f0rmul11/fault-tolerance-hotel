# Сбои на RPC-связях через Envoy

Envoy входит в инфраструктуру `hotelctl up/deploy`, до запуска приложений.
Используется официальный образ 1.37.1 с закреплённым digest. Отдельного
контроллера, собственного образа, service mesh или изменений бизнес-логики нет.
Наблюдаемость сохраняется: Envoy передаёт traceparent/request_id и пишет access log.

После обновления кода собрать CLI и развернуть новые конфигурации/образы приложений:

```sh
go build -o ./bin/hotelctl ./hotelctl/cmd/hotelctl
./bin/hotelctl up
```

`up` не сбрасывает данные. Команду fault запускать в первом терминале, пользовательские
запросы — во втором, после строки ACTIVE:

```sh
./bin/hotelctl fault api-gateway booking --slowdown 8s --duration 10s
./bin/hotelctl fault api-gateway booking --direction response --slowdown 8s --duration 10s
./bin/hotelctl fault hotels review --unavailable --duration 10s
```

Поддерживаются существующие RPC-связи:

| Откуда | Куда | Listener |
|---|---|---:|
| api-gateway | booking | 10001 |
| api-gateway | hotels | 10002 |
| api-gateway | check-in | 10003 |
| booking | hotels | 10004 |
| hotels | review | 10005 |

Пара определяет направление вызова даже при `--direction response`: это ответ Booking
на вызов Gateway. Настройка меняется сразу через Envoy admin runtime; Pod не перезапускается.
Все RPC выбранной связи, включая Echo, подвержены fault. Reflection исключён, HTTP-probes
приложений используют отдельные порты. Kafka и PostgreSQL через этот HTTP/gRPC proxy не идут.

- `--slowdown` — дополнительное ожидание **каждого** подходящего вызова; по умолчанию
  перед отправкой запроса. Допустимо 1ms–1m с точностью до миллисекунды.
- `--direction response` — задержка полностью полученного unary-ответа. Booking может
  уже зафиксировать бронь, когда вызывающая сторона достигает своего deadline.
- `--unavailable` — штатный fault abort с gRPC UNAVAILABLE (14), без вызова downstream;
  нельзя сочетать с slowdown или response. На текущем Gateway это HTTP503.
- `--duration` — окно включения, от 1ms до 1h. Для длинного окна увеличить общий
  `--timeout`, например `--duration 10m --timeout 11m`.

Для ответа используется короткий Lua-фильтр: он буферизует unary-ответ и асинхронно
вызывает приватный listener того же Envoy. Ожидание выполняет штатный HTTP fault filter
этого listener. Lua не делает blocking sleep; дополнительных Go-сервисов нет.
Без fault этот внутренний вызов сразу возвращает 204; дополнительный локальный hop остаётся.
Лимит буфера 4 MiB соответствует небольшим учебным ответам. Streaming business RPC не поддерживаются.

## Окончание эксперимента

CLI ждёт duration, обнуляет только runtime keys выбранной пары, проверяет применённые
значения и выполняет свежий Echo через тот же listener к downstream. Это проверка
транспортного восстановления, не доказательство успешности всех бизнес-сценариев.
Самостоятельно повторите исходное пользовательское действие.

Уже задержанные вызовы могут завершаться ещё до slowdown после снятия правила.
Например, ответ, попавший в последние секунды десятисекундного окна, всё равно ждёт 8s.
График со скользящим окном может восстанавливаться ещё дольше.

Ctrl+C снимает правило через отдельный cleanup context. Таймер живёт в CLI:
после SIGKILL, падения процесса/компьютера или потери admin-соединения нужен явный clear:

```sh
./bin/hotelctl fault api-gateway booking --clear
./bin/hotelctl fault hotels review --clear
```

Clear не требует успешного baseline и может снять оставшийся unavailable. Полный restart
Envoy также очищает runtime overrides, но обрывает активные соединения. Reset данных для
восстановления не нужен. Одновременно выполняется одна изменяющая операция hotelctl.

Приложения получают `SERVICE_TARGETS` через рендеринг Deployment; исходный YAML остаётся
пригоден для прямого локального запуска. Gateway, Booking и Hotels читают override из env.
Envoy admin 9901 доступен CLI только временным loopback port-forward; Service публикует
лишь пять межсервисных listener, приватные listeners ответа наружу не выставляются.

Gateway задаёт общий deadline 5s на обработку входящих HTTP и unary gRPC запросов.
HTTP-заголовок `X-Request-Timeout: 2s` может сократить лимит; отсутствие, некорректное,
неположительное или большее значение оставляет лимит 5s. Более ранний deadline
вызывающей стороны сохраняется. Downstream получает оставшееся время, без нового бюджета
на каждый вызов. Отдельные admin/probe endpoints не затронуты.

С задержкой ответа 8s Gateway возвращает HTTP 504 примерно через 5s: timeout HTTP-клиента
для демонстрации должен быть больше 5s. Бронь к этому моменту уже может быть сохранена.
При повторе используйте тот же idempotency_key. Deadline отменяет context; обработчики и
зависимости должны учитывать отмену. Он не останавливает произвольный Go-код принудительно
и не является таймаутом чтения HTTP-заголовков или записи ответа в сокет.

## Пример частичного отказа

`hotelctl fault hotels review --unavailable --duration 10s`: непустой каталог и карточка
отеля возвращают 503, а карточка номера и чтение существующей брони остаются доступны.
Пустая страница каталога не вызывает Review. Это недоступность одной связи, не остановка Pod.
Новая бронь известного свободного room_id не требует Review; replay старого ключа не заменяет
проверку создания новой брони. После снятия fault повторите те же чтения.
