# Урок 3 · демо 4: потеря ответа, ключ и версия списка

**Показываем:** потерянный ответ не создаёт дубль; новый ключ со старой версией списка не позволяет незаметно создать вторую бронь. Все защиты включены.

## 1. Подготовить стенд

```bash
cd /Users/d.bulykin/Desktop/faut-tolerance-course/hotel
```

В `services/api-gateway/config/config.yaml`: `retry.handlers[0].enabled: false`.

```bash
./bin/hotelctl build booking api-gateway
./bin/hotelctl deploy booking api-gateway
./bin/hotelctl access
```

Открыть Swagger из вывода `access` в **двух вкладках: А и Б**. Для обеих: `X-Demo-Role: GUEST`, одинаковый `X-Demo-Actor`.

Сгенерировать три UUID: гость, ключ A и ключ Б. Скопировать их в Swagger; повторные запросы не должны генерировать новые ключи.

```bash
uuidgen
uuidgen
uuidgen
```

## 2. Получить исходную версию — обе вкладки

Выполнить **GET `/v1/bookings`** от нового гостя.

**Показать:** список пустой, `bookings_version: "0"`. Вкладка Б остаётся с этим состоянием.

Во вкладке А подготовить **POST `/v1/bookings`**:

```json
{
  "room_id": "1",
  "starts_at": "2027-07-20T12:00:00Z",
  "ends_at": "2027-07-21T12:00:00Z",
  "idempotency_key": "<ключ A>",
  "bookings_version": "0"
}
```

Выбрать свободные номер и период; при повторной репетиции изменить даты. Сохранить исходное тело запроса.

## 3. Потерять ответ — терминал

```bash
./bin/hotelctl fault api-gateway booking \
  --direction response --slowdown 8s --duration 1m
```

Дождаться `ACTIVE`. Во вкладке А выполнить POST **один раз**.

**Показать:** HTTP 504 примерно через 5 секунд. Booking успевает сохранить бронь; задерживается ответ.

В терминале нажать **Ctrl+C**, дождаться снятия сбоя.

## 4. Найти результат и повторить — вкладка А

1. Выполнить GET `/v1/bookings`: **одна бронь**, версия списка **1**. Запомнить ID.
2. Повторить POST с **исходным телом**, прежним ключом A и прежней версией **0**.
3. Снова выполнить GET списка.

**Показать:** POST вернул тот же ID; бронь одна, версия списка осталась **1**. Известный ключ обработан раньше проверки версии.

## 5. Проверить состав запроса — вкладка А

В исходном POST оставить ключ A, но изменить `room_id` на `2`.

**Показать:** HTTP 409 — ключ уже связан с другой бронью. Вернуть исходное тело.

## 6. Попробовать новый ключ со старым состоянием — вкладка Б

Отправить POST с ключом **Б**, `bookings_version: "0"` и **другим свободным номером**, например `room_id: "2"`. Даты те же.

**Показать:** HTTP 409 «Список броней изменился…». Другой номер исключает влияние запрета пересечений.

Выполнить GET `/v1/bookings` во вкладке Б.

**Показать:** первая бронь найдена, версия **1**, второй брони нет. Пользователь видит результат своего первого действия и не повторяет его вслепую.

## 7. Показать осознанную новую операцию

Если пользователь действительно хочет **ещё один номер**, в запросе Б заменить только `bookings_version` на **1** и отправить снова.

**Показать:** вторая бронь создана; GET списка возвращает две брони и версию **2**. Отказ по старой версии не занял ключ Б.

## 8. Завершить

```bash
./bin/hotelctl fault api-gateway booking --clear
```

Брони оставить как результат показа. Для следующей репетиции — новый гость, ключи и свободный период. Сбрасывать БД и снимать ограничения не нужно.
